# /review — 記事をレビューする

> **重要**: `reviewed` タグを付与できるのは `/review` スキルのみです。`/spec` と `/article` スキルはセルフレビューを実施しますが、このタグは付与しません。

## ワークフロー

TodoWrite でタスクを管理しながら順に進めてください。

### 1. レビュー対象を確定する

- ユーザーが引数や会話でファイルパス・slug・タイトルを指定している場合はそれを使う
  - 例: `/review docs/specs/rfc6749.md`、`/review rfc6749`、`/review 2026-04-11-what-is-passkey`
- 指定が無い場合は AskUserQuestion で確認する
- 対象ファイルが `docs/specs/` または `docs/articles/` に存在するか確認する
- 既に `reviewed` タグが付いている場合は再レビューか否かをユーザーに確認してから進める

### 2. 記事を読む

対象の `.md` ファイルを Read で全文読む。以下を把握する:

- 記事の種別 (Spec / Article)
- 主張している技術的事実・仕様の内容
- 参照している一次ソース URL (「参考文献」「参考リンク」セクション)
- 内部リンク一覧

### 3. 一次情報を取得する

記事が参照している一次ソースを `WebFetch` で取得する。推奨一次ソース:

- **IETF RFC**: `https://datatracker.ietf.org/doc/html/rfcNNNN` または `https://www.rfc-editor.org/rfc/rfcNNNN`
- **OpenID Foundation**: `https://openid.net/specs/...`
- **W3C**: `https://www.w3.org/TR/...`
- **FIDO Alliance**: `https://fidoalliance.org/specifications/`

記事内に一次ソースが明示されていない場合は、主題から適切な一次ソースを自ら探す。記事が複数の仕様にまたがる場合はそれぞれの一次ソースを取得する。

### 4. 照合・レビューを実施する

一次情報を基準として、記事の各セクションを以下の観点でチェックする:

| チェック観点 | 内容 |
| --- | --- |
| **事実の正確性** | 仕様・機能の説明が一次情報と一致しているか |
| **技術的正確性** | プロトコルフロー・パラメータ・フィールド名・エンドポイントが正しいか |
| **欠落** | 一次情報に記述されている重要な情報が抜けていないか |
| **誇張・過小評価** | 仕様の範囲を超えた主張や、重要性の過大・過小評価がないか |
| **内部リンクの整合性** | リンク先ファイルが存在し、リンクの説明が正確か |

発見した問題は種別 (誤り / 重大な欠落 / 軽微な不正確さ) と該当箇所・根拠を記録する。

### 5. 問題を修正する

| 問題の種別 | 対応 |
| --- | --- |
| **誤り** (事実と異なる記述) | 必ず修正してから `reviewed` タグを付与する |
| **重大な欠落** | 自分で判断して修正する。直接実行（`/work` 経由でない）の場合はユーザーに確認してもよい |
| **軽微な表現の不正確さ** | 指摘のみで `reviewed` タグ付与を妨げない |

修正には Edit ツールを使い、一次情報を根拠として変更を加える。

### 6. `reviewed` タグをフロントマターに付与する

レビューが完了し (誤りがない、または誤りを修正済み) 記事の内容が適切と判断できたら、ファイル先頭にフロントマターを追加する。

CLAUDE.md のルールにより `reviewed` タグ以外の frontmatter は書きません。通常は frontmatter なしの記事への新規追加のみです。ファイルの先頭に以下を追記します:

```markdown
---
tags:
  - reviewed
---

# 記事タイトル
```

> **補足**: `docs/.vitepress/sidebar.mts` の `extractTitle()` はフロントマターブロックを自動スキップして H1 を取得するため、サイドバーやビルドへの影響はありません。

### 7. フォーマット

対象記事 (および修正した他ファイル) を `oxfmt` でフォーマットする:

```bash
npm run fmt
```

修正を加えたレビューでは特にこのステップが重要 — フォーマッタで差分が出たらそれもコミット対象にする。

### 8. ビルド検証

リポジトリルートで:

```bash
npm run docs:build
```

確認事項:

- 警告 (dead link など) なくビルドが成功する
- 対象記事の HTML が正常に生成されている

### 9. コミット

```bash
git add <対象ファイル>
git commit -m "Review: <slug> — mark as reviewed"
```

修正も行った場合:

```bash
git commit -m "Review & fix: <slug> — <修正内容の概要>"
```

## 最終報告

ユーザーへの最終メッセージに以下を含める:

- レビュー対象ファイルパス
- 参照した一次ソース URL
- 発見した問題と対応 (修正 / 指摘のみ / 問題なし)
- `reviewed` タグ付与の完了確認
- ビルド検証結果 (✅ / ‼️)
