# OpenID Foundation DCP WG 活動レポート (2024 年 1 月)

> 執筆日: 2026-05-22（遡及執筆）
> この記事は 2024 年 1 月の活動を遡及的にまとめたレポートです。

## 1. 概要

Digital Credentials Protocols Working Group（以下「DCP WG」）は、Issuer-Holder-Verifier モデルに基づく検証可能クレデンシャル（W3C VC、IETF SD-JWT VC、ISO/IEC 18013-5 mDL など）の発行・提示・交換に関するプロトコル群を所管する OpenID Foundation の WG である。2023 年 8 月に AB/Connect WG の Credentials サブグループから分離して発足し、2024 年 1 月時点では Kristina Yasuda（Microsoft）と Torsten Lodderstedt（SPRIND）が共同議長を務めていた。定例コールは **DCP WG + SIOP call** 名義で APAC 友好枠（火曜 PST midday）と Atlantic / EU 友好枠（木曜 PST 7AM / 4PM CET）の 2 系統が運用されていた。

2024 年 1 月時点の所管文書は OID4VP・SIOPv2・HAIP（OpenID4VC High Assurance Interoperability Profile）が中心であり、**OID4VCI は依然として AB/Connect WG 配下の文書として運用されている** 状態であった。とはいえ DCP WG ML 上では OID4VCI 関連の議論が事実上中心トピックとなっており、本月は次月（2 月）に控える **OID4VCI 1.0 第 1 次 Implementer's Draft (ID1) の公開レビュー開始** に向けた最終調整期間として位置付けられる。

本月の主軸テーマは大きく次の 5 系統である。

- **OID4VCI ID1 に向けた WG Last Call と最終整形**: 1/16 に Kristina Yasuda が ML 上で「実装者ドラフト承認プロセス開始の合意を 1/22 PST までに WG として確認したい」と起案（[#000119](https://lists.openid.net/pipermail/openid-specs-digital-credentials-protocols/Week-of-Mon-20240115/000119.html)）。`openid/OpenID4VCI` リポジトリでは Mike Jones（selfissued）による章別 proofread PR 群（#178〜#191、#180、#185、#186 ほか）が一斉にマージされ、ID1 候補版を整形する作業が集中的に進められた
- **HAIP の DCP WG ドラフト初版公開**: 1/9 に [HAIP with SD-JWT VC draft 00](https://openid.net/specs/openid4vc-high-assurance-interoperability-profile-sd-jwt-vc-1_0-00.html) が公開され、翌 1/10 (UTC) に Torsten Lodderstedt が ML 経由で告知（[#000118](https://lists.openid.net/pipermail/openid-specs-digital-credentials-protocols/Week-of-Mon-20240108/000118.html)）。OID4VCI / OID4VP / SIOPv2 / SD-JWT VC を組み合わせた高保証ユースケース（eIDAS 2.0、政府発行ウォレット）向けの最初の正式 WG ドラフトという位置づけ
- **Joseph Heenan の共同議長就任**: 1/18 Atlantic コールで Torsten が「ドイツウォレットプロジェクト（funke）への注力により WG 時間が減少する」と表明し、Joseph Heenan（Authlete）の共同議長招請が異議なく承認（[議事録 #000131](https://lists.openid.net/pipermail/openid-specs-digital-credentials-protocols/Week-of-Mon-20240122/000131.html)）。この結果 DCP WG は **Kristina・Torsten・Joseph の 3 名共同議長体制** に移行し、これは 2025 年以降も続く運用の基礎となる
- **DCP WG コール時間の恒久化（rotation 廃止）**: 1/19 に Kristina が新コール時間を提示（[#000125](https://lists.openid.net/pipermail/openid-specs-digital-credentials-protocols/Week-of-Mon-20240115/000125.html)）。Atlantic / EU 枠は **木曜 PST 8AM / 5PM CET の毎週固定**（従来の rotation を廃止）、APAC 枠は **火曜 PST noon / NZT 9AM の毎週開催** で 2 か月試行ののち頻度を再評価、というスキーム。12 月の Doodle poll を踏まえた決定だが、APAC 枠については「bi-weekly 希望が多かったが weekly で出席実態を測る」という判断
- **OID4VP の論点蓄積**: `openid/OpenID4VP` リポジトリでは 1 月中に Oliver Terbu（awoie）と Paul Bastian が中心となり、`request_uri` のプライバシー考察、JAR 強制、`x509_san_*` と `direct_post` の組み合わせなど、ID3 マイルストーン向けの issue 群が次々と起票された

主要メンバー（Kristina Yasuda、Torsten Lodderstedt、Joseph Heenan、Daniel Fett、Tobias Looker、Oliver Terbu、Paul Bastian、Brian Campbell、Michael Jones、John Bradley、Christian Bormann、David Chadwick、David Waite、Tim Cappalli、Andrea Vesco（peppelinux）、Giuseppe De Marco、George Fletcher、Mark Haine、Pedro Felix ほか）が議論に参加。DCP WG ML の 2024 年 1 月送信件数は週次インデックスを通算して **約 35 件**（メッセージ番号 000107〜000140 域）で、OpenID Summit Tokyo 2024（1/19 開催）と並行する形で OID4VCI ID1 への最終助走が進んだ月であった。

## 2. 公開された仕様・ドラフト改訂

### HAIP with SD-JWT VC draft 00 公開（1/9）

本月最大の対外的成果は **HAIP（OpenID4VC High Assurance Interoperability Profile）の最初の WG ドラフトが OpenID Foundation の公式 specs リポジトリに公開** されたことである。

- **公開日**: 2024-01-09
- **告知 ML**: 2024-01-10、Torsten Lodderstedt から [#000118](https://lists.openid.net/pipermail/openid-specs-digital-credentials-protocols/Week-of-Mon-20240108/000118.html)
- **エディタ**: Kristina Yasuda（Microsoft）、Torsten Lodderstedt（sprind.org）
- **URL**: [openid4vc-high-assurance-interoperability-profile-sd-jwt-vc-1_0-00.html](https://openid.net/specs/openid4vc-high-assurance-interoperability-profile-sd-jwt-vc-1_0-00.html)
- **プロファイル対象**: OID4VCI / OID4VP / SIOPv2 / SD-JWT VC の 4 仕様
- **想定ユースケース**: 高セキュリティ・高保証要件下のクレデンシャル発行・提示（eIDAS 2.0 準拠ウォレット、政府発行クレデンシャル、エンタープライズウォレット）

HAIP は「相互運用性プロファイル」として、4 つの根拠仕様に対する「どの機能を選ぶか」「どの暗号スイートを必須とするか」「どのフロー組み合わせを mandate するか」を一括して定義する文書である。draft 00 では Issuance 要件（pre-authz / authz code 両フロー必須、sender-constrained tokens）、Presentation Protocol（JAR + direct_post レスポンスモード）、SD-JWT VC のクレデンシャルフォーマット、暗号基盤（P-256 / ES256 / SHA-256 必須）が章立てされている。

このドラフトは後に EUDI ウォレット規定（eIDAS 2.0 ARF）の参照プロファイルとして引用される系譜の起点であり、2024 年 1 月時点ではまだ「文書名に SD-JWT VC を含む」段階だが、後に SD-JWT VC 専用部分と他クレデンシャルフォーマット用部分に分離されていく。

#### PR #177: ID1 向け参照更新（1/12 merge）

Mike Jones 起票。**「Update references in preparation for ID1」** という直截なタイトルが示すとおり、ID1 公開を見据えて draft 文書の normative references / informative references を整える PR。OAuth 2.0 系 RFC、SD-JWT VC ドラフト、ISO 18013-5 等の参照先バージョンの最終確認が行われた。

#### PR #208: Credential Response から `format` を削除（1/16 merge）

Paul Bastian 起票。Issue #204 を解決する PR で、Credential Response から `format` パラメータを除去し、Credential Request 側で format を一意に決定する設計に統一。1/11 Atlantic コール（議事録 [#000130](https://lists.openid.net/pipermail/openid-specs-digital-credentials-protocols/Week-of-Mon-20240122/000130.html)）の「フォーマットは authz request の段階で確定するので response 側に重複を持つ必要がない」という議論の成果。

#### PR #219: Authorization Details への `format` 再追加（1/25 merge）

Torsten Lodderstedt 起票。PR #208 で response から `format` を取り除いた一方、authorization details 側では **「`format` および format specific additional claims を明示するオプション」** を保つかが論点となった。1/18 Atlantic コール（議事録 [#000131](https://lists.openid.net/pipermail/openid-specs-digital-credentials-protocols/Week-of-Mon-20240122/000131.html)）で Torsten が「format 指定オプションの削除は懸念」と表明し、Joseph や Kristina の「サーバーメタデータの mandate は実装複雑化」とする反論と並走した結果、**1/25 コール後に「`format` を authorization details に非必須で再追加する」方向で合意** し、本 PR としてマージ。サーバーメタデータの mandatory 使用に関する再検討は 1 週間以内、と議事録に記録されている。

#### PR #220: `credential_configurations` → `credential_configuration_ids` リネーム（1/25 merge）

Sakurann（Kristina Yasuda）起票。1/25 Atlantic コール（議事録 [#000133](https://lists.openid.net/pipermail/openid-specs-digital-credentials-protocols/Week-of-Mon-20240122/000133.html)）でリネーム提案が紹介され「メタデータ参照との整合性がクリーン」として肯定的フィードバックを受けてマージ。Credential Offer 内で参照しているのは「設定の ID リスト」であって「設定そのもの」ではないという意味的明確化。

#### PR #140 / #170: 署名済み Issuer Metadata と Logo パラメータ（1/10〜1/11 merge）

Sakurann 起票の 2 件。PR #140 は **`signed_credential_issuer_metadata` メタデータパラメータの追加** で、Issuer Metadata を signed JWT として配信し信頼アンカーに紐付ける運用を可能にする。1/4 / 1/11 コール双方で議論され、「`sub` と `iss` クレームが issuer identifier と一致すべき」「複数の信頼アンカーへの対応を検討」と記録されている（議事録 [#000128](https://lists.openid.net/pipermail/openid-specs-digital-credentials-protocols/Week-of-Mon-20240122/000128.html) / [#000130](https://lists.openid.net/pipermail/openid-specs-digital-credentials-protocols/Week-of-Mon-20240122/000130.html)）。PR #170 は `credential_issuer_logo` を Issuer Metadata に追加する非破壊変更。

### 2024-01-04 Atlantic コール（議事録: Joseph Heenan、参加 19 名）

参加者: Joseph Heenan、Kristina Yasuda、Mark Haine、Philipp Lehwalder（Lissi、新規）、Daniel Fett、Pedro Felix、Paul Bastian、Oliver Terbu、Juba（Lissi、新規）、Javier Ruiz、Giuseppe De Marco、Fabian Hauck、Sudesha Shetty、Michael Jones、Brian Campbell、George Fletcher。

年明け最初のコールで、事務連絡と細かい用語整理が中心。

- **新規参加者の IPR 署名**: Lissi の Philipp と Juba に IPR policy 署名を依頼。**「投票権獲得のためのメンバーシップ加入も奨励」** と記録
- **Bitbucket からの通知移行**: GitHub への通知システム移行が ML トラフィック増加を伴うことを受け入れ、承認
- **`encryption_required` 命名合意**: 用語の明確化のため `encryption_required` を採用
- **Credential Logo 構造**: Joseph の懸念を受け、データ構造全体で URI を mandatory 化
- **Notification Endpoint**: イベントは必ずしもエラーではないため `error.description` を `event.description` にリネーム
- **言語識別**: Display 構造を「オブジェクト構造」から「言語キー付きマップ」に変える案が検討されたが、case sensitivity・重複の扱いに懸念。提案者のフィードバック待ちで保留
- **メタデータ署名**: Issuer metadata の signed 配信について、認証器発行者へのバインディング検証の問題提起

## 5. GitHub 上の議論

2024 年 1 月に GitHub 上で起票・進行した重要な issue / PR から、議論が活発であったものを取り上げる。

### [openid/OpenID4VCI#214](https://github.com/openid/OpenID4VCI/issues/214) - cryptographic_binding_methods_supported and cryptographic_suites_supported

- **起票**: Sakurann、2024-01-17
- **論点**: Issuer Metadata の `cryptographic_binding_methods_supported` と `cryptographic_suites_supported` を分離していると、(1) 複数 binding 方式がある場合にどの暗号スイートがどの方式に対応するか不明、(2) 暗号スイートの有効値が credential format ではなく binding 方式に依存すべき、(3) 実際にどの方式が使われるか不明、という構造的問題。提案は **binding 方式をオブジェクト値として、その内部に対応する暗号スイートを含めるパラメータ再設計**
- **状態**: 1/25 コールで `proof_types` のマップ化方針に合意、2/1 マージの PR #235（Sakurann 起票）で着地

### [openid/OpenID4VP#80](https://github.com/openid/OpenID4VP/issues/80) - Privacy considerations on request_uri

- **起票**: Paul Bastian、2024-01-14
- **論点**: `request_uri` 解決を verifier 側で遅延的（lazy）に行う設計が、verifier に対するウォレット capability の不必要な開示につながり、**ユーザフィンガープリンティング** リスクを生む。PR #59 の議論と同根の論点で、後の signed request など派生議論の起点
- **状態**: Issue として 2024 年中議論継続。1/31 APAC コールでも関連議論が記録（議事録 #000140）

### [openid/OpenID4VP#82](https://github.com/openid/OpenID4VP/issues/82) - Add client_id_scheme based on .well-known

- **起票**: Oliver Terbu（awoie）、2024-01-24
- **論点**: 既存の `redirect_uri` / `x509_san_dns` / `x509_san_uri` / `verifier_attestation` に加え、**`.well-known` ベースの client_id_scheme** を追加する提案。verifier が `https://<domain>/.well-known/openid-federation-verifier` 等で公開した metadata と client_id を結びつける運用を想定。後の OpenID Federation との接合点を作る issue として位置づけられる

### [openid/OpenID4VP#79](https://github.com/openid/OpenID4VP/issues/79) - Mandate JAR-encoded Request Objects

- **起票**: Paul Bastian、2024 年 1 月
- **論点**: OID4VP の Request Object を **常に JAR (JWT-Secured Authorization Request) でエンコードすることを必須化** するか。署名・改ざん耐性の保証を仕様レベルで強制するか、`request` / `request_uri` 経由の plain JSON も許すかの設計判断
- **状態**: 1/31 APAC コールおよび後続コールで継続議論

### [openid/OpenID4VP#83](https://github.com/openid/OpenID4VP/issues/83) - Enable x509_san_dns for direct_post without redirect_uri

- **起票**: Oliver Terbu（awoie）、2024 年 1 月
- **論点**: `redirect_uri` client_id_scheme で既に許されている挙動（direct_post を redirect_uri 省略で使う）を `x509_san_dns` 系証明書ベース identification にも揃える設計
- **状態**: PR [#84](https://github.com/openid/OpenID4VP/pull/84)（Oliver Terbu 起票）で解決。1/31 APAC コールで「2/7 ISO WG10 ミーティング前に複数承認必要」と整理され、2/1 にマージ

### [openid/oid4vc-haip-sd-jwt-vc Issue 91](https://github.com/openid/oid4vc-haip-sd-jwt-vc/issues/91)（クローズ）

- ML #000111〜#000112 で 2024-01-03 にコメント追加→クローズが記録。HAIP draft 00 公開直前のクリーンアップに伴う issue 解決として観測されるが、Issue 本文の取得は本稿執筆時点で限定的
