# OpenID Foundation DCP WG 活動レポート (2024 年 2 月)

> 執筆日: 2026-05-22（遡及執筆）
> この記事は 2024 年 2 月の活動を遡及的にまとめたレポートです。

## 1. 概要

Digital Credentials Protocols Working Group（以下「DCP WG」）は、Issuer-Holder-Verifier モデルに基づく検証可能クレデンシャル（W3C VC、IETF SD-JWT VC、ISO/IEC 18013-5 mDL など）の発行・提示・交換に関するプロトコル群を所管する OpenID Foundation の WG である。2023 年 8 月に AB/Connect WG の Credentials サブグループから分離して発足したばかりで、2024 年 2 月時点での共同議長は Kristina Yasuda（Microsoft）、Joseph Heenan（Authlete）、Torsten Lodderstedt（SPRIND）の 3 名体制。定例コールは **DCP WG + SIOP call** 名義で APAC 友好枠（火曜 PST midday）と Atlantic / EU 友好枠（木曜 PST 8AM / 5PM CEST）の 2 系統が運用されていた。

2024 年 2 月時点の所管文書は OID4VP・SIOPv2・HAIP（OpenID4VC High Assurance Interoperability Profile）が中心であり、**OID4VCI は依然として AB/Connect WG 配下の文書として運用されている** 状態であった（DCP WG への正式移管は 4/15 の Call for Adoption 発出を待つ）。とはいえ DCP WG ML 上では OID4VCI 関連の議論が事実上中心トピックとなっており、本月の最大の節目も AB/Connect WG が出した **OID4VCI 1.0 第 1 次 Implementer's Draft (ID1) の公開レビュー開始 (2/8)** であった。

本月の主軸テーマは大きく次の 4 系統である。

- **OID4VCI 1.0 ID1 公開レビュー開始**: 2/8 に Mike Jones が ML に Public Review Period 開始を告知（[#000142](https://lists.openid.net/pipermail/openid-specs-digital-credentials-protocols/Week-of-Mon-20240205/000142.html)）。45 日間の公開レビュー (2024-02-08 〜 2024-03-24) と、3/25 〜 4/1 の OIDF 全会員投票が同時に予告された。投票対象版は [openid-4-verifiable-credential-issuance-1_0-ID1.html](https://openid.net/specs/openid-4-verifiable-credential-issuance-1_0-ID1.html)（draft 13、2024-02-08 発行、エディタは T. Lodderstedt / K. Yasuda / T. Looker）
- **`claims` 定義の構造的破綻問題と PR #276 の起票**: 公開レビュー開始からわずか 5 日後の 2/13 に Daniel Fett が「Credential format profiles: 'claims' definitions are broken」を ML 投稿（[#000145](https://lists.openid.net/pipermail/openid-specs-digital-credentials-protocols/Week-of-Mon-20240212/000145.html)）し、Issue [#266](https://github.com/openid/OpenID4VCI/issues/266) を起票。OID4VCI Appendix A の 3 プロファイル共通で nested claims や arrays が正しく表現できないという根本的な指摘であり、**「公開レビュー開始直後に breaking change が必要かもしれない」** という緊迫した状況を WG にもたらした。2/15 Atlantic コールで「breaking change を受け入れる」方向に合意、2/20 に Daniel Fett が PR [#276](https://github.com/openid/OpenID4VCI/pull/276)（claims path query / claims display description の導入）を起票
- **Presentation Exchange の代替を巡る議論の発火**: 2/15 に Orie Steele（Transmute）が「A simple presentation endpoint」を ML 投稿（[#000153](https://lists.openid.net/pipermail/openid-specs-digital-credentials-protocols/Week-of-Mon-20240212/000153.html)）し、OID4VP の複雑さに対して「`GET /nonce` と `POST /presentations` だけの極小エンドポイント」案を提示。Brian Campbell・Joseph Heenan・Kristina Yasuda らが discovery・OAuth との関係・複数フローの扱いを巡って反論し、**3 月以降の Presentation Exchange 後継議論（Oliver Terbu のフォーマット固有クエリ言語、Sakurann の Issue #129、Tobias の Issue #136）の伏線** となるスレッドが立ち上がった
- **OID4VP の Implementer's Draft 3 (ID3) に向けた地ならし**: `openid/OpenID4VP` リポジトリで 2 月に **9 件の PR がマージ**（PR #84 / #92 / #97 / #101 / #104 / #108 / #110 / #72 / #76）。`x509_san_*` と `direct_post*` の組み合わせ許可（PR #84）、`access_denied` エラーパラグラフ追加（PR #97）、direct_post のエラー例追加（PR #108）など、ID3 ターゲットの素地が積み上がった。一方で長期 PR である [#59](https://github.com/openid/OpenID4VP/pull/59) (request_uri extension、2023-11-02 起票) は **2 月中は議論が停滞** し、再活発化は 3 月後半まで待たれることになる

主要メンバー（Kristina Yasuda、Joseph Heenan、Torsten Lodderstedt、Daniel Fett、Tobias Looker、Oliver Terbu、Paul Bastian、Brian Campbell、Michael Jones、John Bradley、Christian Bormann、Jan Vereecken、David Chadwick、David Waite、Tim Cappalli、Tom Jones、Andrea Vesco（peppelinux）、Christian Bormann、Sebastien Bahloul、Babis Routis（c2bo）他）が議論に参加。`openid-specs-digital-credentials-protocols` 上の 2 月送信投稿は通算 **約 50 件**（メッセージ番号 000141〜000189 域、HAIP リポジトリの bot 投稿を含む）で、2/15 Atlantic コール直後の Daniel Fett 投稿を起点に「PE 後継」「`claims` 定義」「ID1 投票」の 3 ライン並走となった。

## 2. 公開された仕様・ドラフト改訂

### OID4VCI 1.0 ID1 公開レビュー開始（2/8）

本月最大のマイルストーンは **OID4VCI 1.0 を OpenID Implementer's Draft (ID1) として承認するための公式手続きが開始** されたことである。

- **告知発出**: 2024-02-08、Michael Jones から ML に [Public Review Period for Proposed Implementer's Draft of OpenID for Verifiable Credential Issuance](https://openid.net/review-of-proposed-implementers-draft-of-openid-for-verifiable-credential-issuance/) として送信（[ML #000142](https://lists.openid.net/pipermail/openid-specs-digital-credentials-protocols/Week-of-Mon-20240205/000142.html)）
- **公開レビュー期間**: 2024-02-08 〜 2024-03-24（45 日間）
- **Notice of Vote 予定**: 2024-03-11
- **早期投票開始予定**: 2024-03-18（レビュー完了済みメンバー向け）
- **公式投票期間予定**: 2024-03-25 〜 2024-04-01（7 日間）
- **レビュー対象版**: [openid-4-verifiable-credential-issuance-1_0-ID1.html](https://openid.net/specs/openid-4-verifiable-credential-issuance-1_0-ID1.html)（draft 13、エディタ T. Lodderstedt / K. Yasuda / T. Looker、2024-02-08）

告知本文は「The OpenID Connect Working Group recommends approval of the OpenID for Verifiable Credential Issuance 1.0 specification as an OpenID Implementer's Draft」と、AB/Connect WG（当時 OpenID Connect WG とも呼ばれる）名義で発出されている点が重要である。2024 年 2 月時点では OID4VCI は AB/Connect WG の文書であり、DCP WG への所管移管は ID1 承認後の Call for Adoption（後の 4/15 発出）以降であった。一方で実際の議論は DCP WG ML 上で行われており、**形式的所管と実質的議論場の乖離** が本月のメタな特徴となっていた。

#### PR #235: `proof_types` のマップ化（2/1 merge）

Sakurann（Kristina Yasuda）起票。Issue [#214](https://github.com/openid/OpenID4VCI/issues/214) と Issue [#37](https://github.com/openid/OpenID4VCI/issues/37) を解決する破壊的変更で、`cryptographic_suites_supported` を `credential_signing_alg_values_supported` にリネームし、`proof_types` を配列から `proofs_supported` マップに構造変更。各エントリ内に `proof_signing_alg_values_supported` を必須とすることで空オブジェクトを排除する設計。**ID1 公開直前の構造変更** であったが、複数レビュアの承認を得て 2/1 に滑り込みマージされた。

#### PR #84: `x509_san_*` と `direct_post*` の組み合わせ許可（2/1 merge）

Oliver Terbu（awoie）起票。Issue [#83](https://github.com/openid/OpenID4VP/issues/83) を解決する PR で、`x509_san_*` 系 client_id_scheme について `redirect_uri` を省いた `direct_post` / `direct_post.jwt` を許可する文言を追加。redirect_uri client_id_scheme で既に許されていた挙動を、証明書ベース identification にも揃える形。1 月時点の PR を 2 月初頭にマージ。

#### PR #97: `access_denied` エラーパラグラフ追加（2/20 merge）

Oliver Terbu 起票。Issue [#89](https://github.com/openid/OpenID4VP/issues/89) を解決する非破壊変更で、Response Error セクションに `access_denied` を追加。これは **「ウォレットが要求されたクレデンシャルを保有していない」場合のエラーコード**。レビュー中に Sakurann が「専用エラーコードを切るべきでは」と問題提起したが、**「専用コードは『ウォレットがどの credential を持たないか』をリーク しうるためプライバシー上避けたい」** という議論を経て `access_denied` 流用で着地した。`/review` の文脈で説明される非破壊化の好例である。

#### PR #108: direct_post のエラー例追加（2/21 merge）

Oliver Terbu 起票。Issue [#88](https://github.com/openid/OpenID4VP/issues/88) 関連で、Authorization Error Response の direct_post 経由 例を追加。Response Endpoint が両ケース（成功 / エラー）で `redirect_uri` パラメータを返せることを明示。jogu・c2bo・Sakurann・adeinega の 4 名承認でマージ。

### 2024-02-01 Atlantic コール（議事録: Joseph Heenan、原稿: Oliver Terbu）

ID1 公開直前のクリーンアップ回。OID4VP の PR [#84](https://github.com/openid/OpenID4VP/pull/84)（response_uri/client_id_scheme の整理、4 承認獲得済み）のマージ承認、OID4VCI PR [#235](https://github.com/openid/OpenID4VCI/pull/235)（`proof_types` マップ化）の最終調整版承認、PR [#249](https://github.com/openid/OpenID4VCI/pull/249)（pre-auth-only AS の `response_types_supported` 省略許可、RFC 8414 との非整合解消）の SHOULD→MAY 緩和合意などが立て続けに決定。Privacy considerations を扱った PR [#187](https://github.com/openid/OpenID4VCI/pull/187) では「issuer consent をウォレット配信時に要求」「`valid` という用語を `no longer verifiable` に置換」といった用語面の合意も得られた。PR [#243](https://github.com/openid/OpenID4VCI/pull/243) のエディトリアルは Joseph の懸念がほぼ解消され再レビュー回付。

### 2024-02-15 Atlantic コール（議事録: Joseph Heenan、参加 22 名）

参加者: Kristina Yasuda、Brian Campbell、Daniel Fett、David Waite、Jan Vereecken、John Bradley、Michael Jones、Oliver Terbu、Tim Cappalli ほか（David Chadwick 含む 22 名、David は遅参のため当初の議事録から漏れたが #000165 で本人指摘・#000176 で Joseph が訂正）。

**最大の議題は VCI claims metadata 問題**。Daniel Fett が「nested 構造での衝突」「arrays の扱いの未定義」を改めて提示し、**「現行アプローチを継続するのではなく breaking change 解で対処する」** ことで WG 合意。提示された複数案のうち **「solution 1.iii（arrays as pointers アプローチ）」が最もクリーンに問題を解決する** として支持を集めた。Brian Campbell は別途 ML #000148 で「会議に断続参加だが solution 1.3 (arrays as pointers) 支持、加えて option 3 の併用も検討に値する。SD-JWT VC Type Metadata にも同方針を適用すべき」と表明。

決定事項は以下:

- Daniel Fett: solution 1.iii を実装する PR を作成（→ 2/20 起票の PR [#276](https://github.com/openid/OpenID4VCI/pull/276)）。arrays の null 構文を `-1` に置換
- Joseph Heenan: Issue [#95](https://github.com/openid/OpenID4VP/issues/95) を扱う PR を準備（OID4VP）
- Jan Vereecken: Issue [#74](https://github.com/openid/OpenID4VP/issues/74) の PR を準備
- Kristina Yasuda: PR [#97](https://github.com/openid/OpenID4VP/pull/97)（`access_denied`）を提示、ウォレットがクレデンシャル不足の場合のエラー扱いを問題提起

claims metadata 議論は **「公開レビュー開始後だが、breaking change を含む実装経験を蓄積した上で必要ならレビュー期間を再延長する」** という構えが共有された点が重要である。OIDF の Implementer's Draft 手続きでは、レビュー期間中に大きな仕様変更があれば 45 日間レビューを再起動するのが規則であり、ID1 投票スケジュール（3/25〜4/1）への影響を孕んだ判断であった。

### [Public Review Period for Proposed Implementer's Draft of OpenID for Verifiable Credential Issuance](https://lists.openid.net/pipermail/openid-specs-digital-credentials-protocols/Week-of-Mon-20240205/000142.html) - 2024-02-08 開始

### [Credential format profiles: 'claims' definitions are broken](https://lists.openid.net/pipermail/openid-specs-digital-credentials-protocols/Week-of-Mon-20240212/000145.html) - 2024-02-13 開始

**ID1 公開レビュー開始からわずか 5 日後** に Daniel Fett が投稿した、本月最大の技術論点。

> as discussed in today's call, there is a problem in the definition of the credential format profiles that may or may not stop us from going ahead with the implementers draft.
> （[#000145](https://lists.openid.net/pipermail/openid-specs-digital-credentials-protocols/Week-of-Mon-20240212/000145.html) より）

ML 上ではポインタ短信で、詳細は Issue [#266](https://github.com/openid/OpenID4VCI/issues/266) に展開。Issue 本文では Appendix A の 3 つのクレデンシャルフォーマットプロファイル（ldp_vc、jwt_vc_json、jwt_vc_json-ld または mso_mdoc 系）で:

1. `mandatory` という構文要素名と、クレームの literal 名「mandatory」の区別がつかない
2. `address` とそのサブクレーム `address/region` のような階層を表現できない
3. オブジェクトが「クレームの属性」を表すのか「ネストされたクレーム」を含むのか、パース時に判別困難
4. 配列の扱いが完全に未定義

の 4 点を構造的問題として指摘。

返信は Tom Jones が #000146 で **「I have a fundamental problem with the direction of this work. It is becoming so complex that very idea of conformance is becoming impossible. I will not be building a wallet that supports all the items that are required.」** と、**仕様全体の方向性に対する根本的な異議** を表明。「複雑性が増しすぎて準拠そのものが実現不能になりつつある」とする Tom の立場と、「ID1 直前でも構造を正すべき」とする Daniel の立場の対比が、本スレッドの基本構図となった。

WG としては 2/15 Atlantic コールで「breaking change 解で対処」と合意し、Daniel は 2/20 に PR [#276](https://github.com/openid/OpenID4VCI/pull/276) を起票。PR は 2/21 APAC コールで「great improvement」と評価される一方、2/29 Atlantic コールでは **ID2 への延期** が示唆される、というジグザグな推移を辿った。最終的にこの問題（claims path query / claims display description の導入）は ID1 サイクルでは解決されず、2024 年末まで継続議論された。

### [A simple presentation endpoint](https://lists.openid.net/pipermail/openid-specs-digital-credentials-protocols/Week-of-Mon-20240212/000153.html) - 2024-02-15 開始

Orie Steele（Transmute Industries CTO）が ML 投稿した、**OID4VP の複雑性そのものに対する原理的問題提起**。

Orie の提案: 「ウォレットがプレゼンテーションを送る方法は、本質的に `GET relying-party.example/nonce` と `POST relying-party.example/presentations` の 2 エンドポイントで足りる」。nonce・クレデンシャルタイプ・claims・エンドポイントの所在は out-of-band でネゴシエートされる前提で、署名済み・暗号化済みプレゼンテーションは API gateway フィルタで対処、というミニマリスト設計を主張。「all the parameters that are 'not a nonce' and 'not a presentation' are getting in the way of a simple spec」と、OID4VP の複雑性に対する痛烈な批判。

これに対して反論が集中:

- **Brian Campbell** (#000155 系列): 「ウォレット側がこのエンドポイントの存在をどう知るのか（discovery）。レスポンスは何を返すのか」と、**実装上の現実的ギャップ** を指摘
- **Joseph Heenan** (#000156): 「これは OAuth ベースのフローではない？ もしそうでないなら、verifier とウォレットのセッション連結はどう行うのか。RP がクレデンシャルを欲していることをウォレットはどう知るのか」と、**OAuth とのリンク・use case の不明確さ** を問題化
- **Kristina Yasuda**: 「1 つのエンドポイントが複数フローを担うべきではない」と分離主張

Orie の再反論 (#000170): **「token endpoint や OpenID configuration endpoint は 1 つで複数フローを担う先例があり、`response_mode` のようなパラメタライゼーションで対応可能。エンドポイント仕様は両フロー、あるいは複数プロトコルを横断して機能しうる」**。

このスレッドは 2 月中に合意に達することはなかったが、**Presentation Exchange の代替を巡る議論が DCP WG 全体の中心トピックに浮上する転機** となった。3/5 の Oliver Terbu によるフォーマット固有クエリ言語提案（#000192）、3/11 の Orie Steele 自身による PEv1 凍結+PEv2 別ドキュメント化案（#000207）、3/12 の Sakurann による Issue [#129](https://github.com/openid/OpenID4VP/issues/129)（MTI 最小プロファイル）への分岐が、本スレッドの直接の系譜にあたる。

## 5. GitHub 上の議論

2024 年 2 月に GitHub 上で起票・進行した重要な issue / PR から、議論が活発であったものを取り上げる。

### [openid/OpenID4VCI#266](https://github.com/openid/OpenID4VCI/issues/266) - Credential format profiles: 'claims' definitions should be improved

- **起票**: Daniel Fett、2024-02-13
- **状態**: Closed（PR [#276](https://github.com/openid/OpenID4VCI/pull/276) でマージ）
- **論点**: 上記 §4 で詳述。本月の OID4VCI 側で最大の技術 issue。Appendix A の 3 プロファイル共通で nested claims・arrays が表現不能であるとする 4 点指摘。**ID1 公開レビュー開始からわずか 5 日後の起票** が WG に与えたインパクトが大きく、2/15 Atlantic / 2/21 APAC / 2/29 Atlantic の 3 コールで連続議論された

### [openid/OpenID4VCI#276](https://github.com/openid/OpenID4VCI/pull/276) - Define claims display description and claims path query

- **起票**: Daniel Fett、2024-02-20
- **状態**: 最終的に 2024-12-17 にマージ（10 か月議論）
- **論点**: Issue #266・#271・#272 を解決。`claims` 定義に「claims display description」と「claims path query」（JSON path 構文によるネスト参照）を導入。レビューでは「破壊的変更だが既存実装はほぼ確定している」として **配列ベース solution に対する違和感** を表明する声と、「ID1 後の修正で対応可能」とする声が並走。**ID1 サイクルに間に合わせるか否か** の判断が 2/29 コールで「ID2 延期」傾向に振れる。最終的に 9 名から承認を得て大幅修正版でマージ

### [openid/OpenID4VCI#278](https://github.com/openid/OpenID4VCI/issues/278) - Supporting Credential Versioning

- **起票**: Tobias Looker（tplooker）、2024-02-23
- **状態**: ラベル `has-PR`、`ready-for-PR`、マイルストーン「1.1 or later」
- **論点**: ウォレットが同一クレデンシャルの複数コピーを保持する場合（unlinkable presentations 目的、属性更新後の新版取得目的）、**「2 つのコピーが等価か（claims / values が一貫しているか）をウォレットがどう判定するか」** という根本問題。Tobias の提案は (1) credential response に `version_id` フィールド追加、(2) `/credential/updates` エンドポイント新設、の 2 段構え。2024 年 2 月時点では「1.1 or later」スコープと整理され、ID1 サイクルには含めない方針

### [openid/OpenID4VCI#265](https://github.com/openid/OpenID4VCI/issues/265) - aud Claim Value in JWT Proof Sent to Credential Endpoint

- **起票**: Andrea Vesco（peppelinux）、2024-02-13
- **論点**: Credential エンドポイントに送る JWT Proof の `aud` クレーム値を **issuer entity identifier ではなく実際の HTTP エンドポイント URL** に揃えるべき、という提案。利点として (1) エンドポイント specific の誤用防止、(2) OAuth 2.0 token endpoint 慣行との整合、(3) 異種クレデンシャルタイプごとの複数エンドポイント対応、(4) entity ID マッピングを要さない検証単純化、の 4 点を提示。PR [#188](https://github.com/openid/OpenID4VCI/pull/188) で解決方針、マイルストーン「1.1 or later」

### [openid/OpenID4VP#106](https://github.com/openid/OpenID4VP/issues/106) - Client metadata needs to indicate what keys are meant for jarm encryption

- **起票**: Oliver Terbu（awoie）、2024-02-16
- **論点**: JARM / ISO 18013-7 暗号化実装で、client metadata に署名検証鍵と暗号化鍵が混在する場合に **「どの鍵がどの目的か」を識別する仕組みが欠落** している。提案は後方互換性のある `encryption_keys` パラメータ（`jwks` 配列内 JWK の `kid` を列挙）の導入。ISO 18013-7 では signature verification key を暗号化に使わないため後方互換性懸念なし

### [openid/OpenID4VP#100](https://github.com/openid/OpenID4VP/issues/100) - Option missing for non-valid OpenID4VP requests

- **起票**: Oliver Terbu（awoie）、2024-02-27
- **論点**: 無効な OID4VP リクエストに対するエラー応答オプションが欠落。PR [#101](https://github.com/openid/OpenID4VP/pull/101)（2/27 マージ）で解決
