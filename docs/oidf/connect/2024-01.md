# OpenID Foundation AB/Connect WG 活動レポート (2024年1月)

> 執筆日: 2026-05-22（2024 年 1 月の活動を遡及してまとめたレポートです）

## 1. 概要

AB/Connect Working Group（AB/Connect WG）は、OpenID Connect 仕様群および OpenID Federation 系仕様を策定する OpenID Foundation 最古参の WG である。2024 年 1 月時点の共同議長は Nat Sakimura、Michael B. Jones、John Bradley の 3 名。当時、議事録は ML 公開アーカイブ（`openid-specs-ab`）にスレッドとして投稿され、Issue は Bitbucket（`bitbucket.org/openid/connect`）で管理されるという運用が継続していた。なお当時、OID4VCI / OID4VP / SIOPv2 を扱う「Digital Credentials Protocols (DCP)」サブグループは AB/Connect WG 配下に位置しており、独立した WG への分離は同年 7 月以降である。

2024 年 1 月は、AB/Connect WG にとって **「OpenID Connect 仕様策定 10 周年を東京で公に祝った月」** であり、同時に **「OID4VCI 1.0 を第 1 次 Implementer's Draft へ昇格させるための WG Last Call を開始した月」** にあたる。1/19 開催の OpenID Summit Tokyo 2024 には 250 名超が参加し、Mike Jones・Nat Sakimura・Nov Matake・Ryo Ito による 10 周年パネルが行われた。同 19 日には Mike Jones を含む 2024 年 OpenID Foundation 理事会選挙の結果が公表されている。

月内の `openid-specs-ab` ML 投稿は #010185 〜 #010219 の計 35 通。Bitbucket Issue は #2102 〜 #2110 の **9 件** が新規起票され、Stefan Santesson（Swedish Federation 実装者視点）と Michele D'Amico（peppelinux、Italian Federation 実装者視点）からの Federation 仕様に対する具体的な指摘が大半を占めた。仕様ドラフトの新規公開（draft 33）は 1 月内には行われず、2023-12-04 公開の OpenID Federation 1.0 draft 32 を題材としてレビューと Issue 起票が進む期間であった。OAuth 2.0 Protected Resource Metadata draft -02 が 1/24 に IETF へ提出され、Native SSO・Federation・OID4VCI を 3 月の IETF 119（Brisbane）に向けて整える助走期にも当たる。

当月の主要トピックは大きく次の 5 系統に整理できる。

- **OpenID Connect 10 周年と OpenID Summit Tokyo 2024 (2024-01-19)**: Shibuya にて OIDF-J 主催で開催。Gail Hodges（OIDF Executive Director）が 2024 年戦略アウトルックと 2023-11 パリの SIDI Summit を報告し、Mike Jones モデレートのもと Nat Sakimura・Nov Matake・Ryo Ito が「なぜ OpenID Connect は成功したか」を議論
- **OID4VCI 1.0 第 1 次 Implementer's Draft 承認プロセス開始**: 1/16 〜 1/22 に Kristina Yasuda が WG Working Group Last Call を実施し、ノーマティブ変更なしで承認プロセスを開始する旨のコンセンサスを確認。後続の 2/8 Public Review 開始（45 日間）に直結する事務手続きの第一歩
- **OpenID Federation 1.0 draft 32 に対する集中レビューと Bitbucket Issue #2102 〜 #2110 の起票**: Stefan Santesson（#2102・#2103・#2104・#2107）、Michele D'Amico（#2105・#2106）、Michael Fraser（#2109）、peppelinux（#2110）から、Entity Statement / 制約定義 / Trust Mark / クライアント認証 / Listing Endpoint 設計に関する具体提案が連続提出
- **認可エンドポイントへの POST サポート問題の再浮上**: 1/8 Spec Call と 1/11 Spec Call で「OIDC Core は GET/POST 両対応を MUST と規定するが、認定スイートが POST テストを実施していない」「FHIR SMART が POST を必須としていて米国連邦法化されている」という事実が共有され、認定スイート（conformance-suite）への警告テスト追加と FHIR 連携が短期アクションとして合意
- **Native Identity Schemes トラッキング (#2108) の開始**: Nat Sakimura が「OpenID Connect を採用している各国 National Identity Scheme」を Bitbucket wiki で追跡する取り組みを 1/16 に開始。コミュニティに国名と一次情報の追加を呼びかけ

## 2. 公開された仕様・ドラフト改訂

### OpenID for Verifiable Credential Issuance 1.0 - 第 1 次 Implementer's Draft 向け WG Last Call (2024-01-16 開始)

1 月最大の節目は、OID4VCI 1.0 を第 1 次 Implementer's Draft (ID1) として承認するための **WG Last Call 開始** である。Kristina Yasuda は [ML #010203](https://lists.openid.net/pipermail/openid-specs-ab/2024-January/010203.html) で、2024-01-16 〜 2024-01-22 (PST 終了) の **1 週間** で WG の合意形成（critical issue の有無確認）を求めた。

- **対象**: 現行 OID4VCI ドラフト文書（normative change なし、editorial のみで Implementer's Draft 化）
- **承認プロセス（3 段階）**:
  1. WG Working Group Last Call（critical issue 特定、1 週間）
  2. OpenID Foundation 全体 Public Review（45 日間）
  3. Membership Vote（7 日間）
- **当時の WG 帰属**: OID4VCI は AB/Connect WG の SIOP/DCP サブグループの成果物として運営されており、独立した Digital Credentials Protocols WG への分離は 2024 年後半に予定

Michael Jones は [ML #010204](https://lists.openid.net/pipermail/openid-specs-ab/2024-January/010204.html) で正式な WG Last Call 通知を発出。スレッドは Kristina Yasuda → Michael Jones → Joseph Heenan → Michael Jones → Arjen van Veen の応答を経て、月内に critical issue は提起されず、2 月の Public Review 開始（[ML #010233](https://lists.openid.net/pipermail/openid-specs-ab/2024-February/010233.html)、2024-02-08）に直結する。Jones は「ワーキンググループがこの重要なマイルストーンに到達したこと」を祝う旨を強調した。

### OpenID Federation 1.0 draft 32 に対する集中レビュー期間

1 月中に新たな Federation draft（draft 33）が公開された事実はなく、月内のレビュー対象は **2023-12-04 公開の draft 32** であった。draft 32 は、2023-11-08 公開の draft 31 で実施された「全節のリライト・簡素化・`trust_mark_owners` への用語統一」（Mike Jones [self-issued.info 2023-11-08 投稿](https://self-issued.info/?p=2464)）を踏まえ、説明改善と「次の Implementer's Draft の基礎」と位置付けられたバージョンである。

1 月の議論は、この draft 32 を Swedish Federation / Italian Federation の実装観点で読み解き、不明瞭点と拡張案を Bitbucket Issue として起票する形で進行した（§ 2 の Bitbucket Issue 表を参照）。これらの Issue は 2/23 公開予定の draft 33 に向けた素材として蓄積された。

### OAuth 2.0 Protected Resource Metadata draft -02（IETF, 2024-01-24）

[Mike Jones の 2024-01-24 投稿](https://self-issued.info/?p=2486) によれば、Aaron Parecki と Mike Jones は同日に `draft-ietf-oauth-resource-metadata-02` を IETF に提出した。IETF 118（2023-11、Prague）での議論を反映した 2 点の変更を含む:

- **メタデータ URL 構築**: 従来のリソース識別子末尾に `.well-known` を連結する方式から、**host と path の間に `.well-known` を挿入する方式** へ変更
- **WWW-Authenticate ヘッダー**: 返却パラメータを `resource` から `resource_metadata` へ変更

本仕様は AB/Connect WG 直管理ではないが、エディタの一方が Mike Jones（AB/Connect WG 共同議長）であり、`openid-specs-ab` でも認知が共有された。3 月の IETF 119 提出物群の助走に位置付けられる。

## 4. メーリングリストの主要スレッド

1 月の `openid-specs-ab` ML には合計 35 通の投稿があった。技術的に重要な 5 本を取り上げる。

### [Issue #2102: New Entity Statement for subject data publication](https://lists.openid.net/pipermail/openid-specs-ab/2024-January/010185.html) - 2024-01-02 起票（Stefan Santesson）

Stefan Santesson が Swedish OpenID Connect federation の実装経験から、**Entity Statement に「subject の Entity Configuration がどこにどう公開されているか」を示す新クレームの追加** を提案。

- 動機: Entity Configuration を発行できない leaf entity を、上位 Entity Statement から validate 可能にする
- 効用: (1) leaf entity が Entity Configuration を出さず simplified operation を選択できる、(2) discovery で無駄なリトライが減る、(3) top-down traversal で federation 階層を辿る resolver の動作を支援
- 背景: Swedish Federation 配備において、Entity Configuration を publish できない事業者を含めるユースケース

このスレッドは Federation 仕様の「discoverability vs validatability」というトレードオフを浮き彫りにし、後続の Issue #2104（trust marks in subordinate statements）と組み合わせて Santesson の提案群を構成する。

### [Issue #2103: Ambiguities in the definition of constraints](https://lists.openid.net/pipermail/openid-specs-ab/2024-January/010190.html) - 2024-01-08 起票（Stefan Santesson）

Stefan Santesson が、Entity Statement の制約定義に関する 2 点の曖昧さを指摘。

- **naming constraints の曖昧さ**: 仕様は RFC 5280 に倣うと主張するが、例示は RFC 5280 の複雑性を満たしていない。制約は (a) EntityIdentifier の完全一致リスト、(b) sub-path 拡張可能な base URL、(c) RFC 5280 ホスト名 のどれを意図しているかが不明
- **`allowed_leaf_entity_types` の曖昧さ**: leaf entity metadata の entity type identifier と比較するが、エンティティは federation endpoint 種別の下に共通 metadata を宣言できるため、「中間ロールを避けているか」の判定が複雑になる

Santesson の解決案は「**全ての federation service が role 専用 entity type のみで metadata を宣言する**」（RP は `openid_relying_party`、OP は `openid_provider`、`federation_entity` はインフラロール専用に予約）。この提案は draft 33（2/23 公開）の整理にも影響を与える方向性となった。

### [Issue #2104: Allow trust marks in subordinate statements](https://lists.openid.net/pipermail/openid-specs-ab/2024-January/010198.html) - 2024-01-12 起票（Stefan Santesson）

Stefan Santesson が、現行仕様の Section 3 にある「`trust_marks` claim MUST NOT appear in Subordinate Statements」という制限を不要なものとして撤廃を提案。

- 既に subordinate Entity Statements 内で subject の metadata を伝送できる
- Trust Mark は cryptographically signed で subject に bind されており、セキュリティリスクは限定的
- 制限の撤廃で「Entity Configuration を発行しない end entity を subordinate Entity Statement で完全に表現する」運用が可能になる
- たとえ標準化されなくとも、interoperability 用に critical 拡張としての voluntary な利用を妨げるべきでない

本 Issue は § 4 で紹介した #2102 とセットで「Swedish Federation 系の leaf entity 表現拡張」シリーズを構成し、2 月以降の議論にも継続して影響する。

### [Issue #2107: Relax client assertion requirements and extensibility](https://lists.openid.net/pipermail/openid-specs-ab/2024-January/010201.html) - 2024-01-15 起票（Stefan Santesson）

Stefan Santesson が Trust Mark エンドポイントのクライアントアサーション要件を批判。

- 現行: Trust Mark リクエストは「subject の federation key で署名された自己署名クライアントアサーション」を含めねばならない
- 問題: ホスティング中間業者を経由する低性能 federation service の利用を阻む
- Santesson の論拠: **Trust Mark は subject の鍵に bind されない public information**（「Entity Identifier が defined の subject が valid な Trust Mark を持つ」と主張するに過ぎない）。厳格な署名要件は過剰
- 提案:
  1. Trust Mark subject 以外による署名クライアントアサーションを許容
  2. Trust Mark Issuer が delegate（ホスティング中間業者等）からのリクエストを authorize できる仕組み
  3. delegate リクエスト向けの代替クライアントアサーションタイプを定義
  4. プロファイル独自の追加アサーションタイプを許容（現状の固定値 `urn:ietf:params:oauth:client-assertion-type:jwt-bearer` 一辺倒を緩和）

Santesson は「単一の固定値しか受け付けないなら、なぜ `client_assertion_type` パラメータが存在するのか」と仕様設計の整合性を問うた。

### [Issue with smart app and POST](https://lists.openid.net/pipermail/openid-specs-ab/2024-January/010212.html) - 2024-01-23 起票（Tom Jones）

Tom Jones が、認可エンドポイントの POST メソッド対応に関する論点を再度提起。

- OIDC Core: 「Authorization Server SHALL support the use of the HTTP GET _and POST_ methods at the Authorization Endpoint.」
- 1/22 Spec Call の議事録未投稿点を指摘
- 「POST を deprecate する」決定がいつ・なぜなされたのかの履歴開示を要求
- FHIR SMART App launch documentation は OIDC Core の POST 要件と整合的になっていない点を問題視
- 自ら POST 要件の実態調査と SMART App コミュニティへの follow-up を引き受け

本投稿は 1/8・1/11 Spec Call、1/22 Spec Call で繰り返し議論された認証スイート整備の動きと連動し、月末時点で「警告レベルのテスト追加」「FHIR 関係者と Tom Jones が調整」という方向感が定着した。本論点は 2 月の Issue #2115（Joseph Heenan 起票）として正式化される。

## 5. GitHub 上の議論

2024 年 1 月時点では、AB/Connect WG の Issue Tracker は依然として **Bitbucket（`bitbucket.org/openid/connect`）** で運用されており、GitHub 上の OpenID 配下リポジトリ（`openid/connect`、`openid/OID4VCI`、`openid/OID4VP` 等）の Issue / PR 活動は限定的だった。Bitbucket Cloud は SPA レンダリングのため WebFetch から本文を直接取得できないため、本レポートでは Bitbucket Issue の本文を ML へのクロスポスト経由で再構成した（§ 2、§ 4 に統合）。

1 月中に GitHub 側で並行進行していた主な作業:

- **`openid/OID4VCI` / `openid/OID4VP`（DCP 系リポジトリ）**: SIOP/DCP Sub-call で議論された display オブジェクトのマップ化 PR（後にクローズ）、署名付き Issuer Metadata の処理ルール、credential response からの format パラメータ削除提案など。各議事録（[#010214](https://lists.openid.net/pipermail/openid-specs-ab/2024-January/010214.html)、[#010215](https://lists.openid.net/pipermail/openid-specs-ab/2024-January/010215.html)、[#010216](https://lists.openid.net/pipermail/openid-specs-ab/2024-January/010216.html)）に詳細
- **`openid/conformance-suite`（GitLab ベースだが ML で議論）**: 認可エンドポイント POST テスト追加の作業着手が 1/11 Spec Call で合意。月内の具体的な PR / Issue 番号は ML 上では確認できなかった

これらは AB/Connect WG 直下の管理対象ではあるが、議論の主戦場は SIOP/DCP サブグループとして AB/Connect WG ML に集約されていた。GitHub 検索クエリ `is:issue created:2024-01-01..2024-01-31` および `is:pr created:2024-01-01..2024-01-31` を `openid/connect` リポジトリに対して実行しても実質ゼロであり、1 月の議論実体は Bitbucket Issue #2102 〜 #2110 のクロスポストに集約される。
