# OpenID Foundation AB/Connect WG 活動レポート (2024年3月)

> 執筆日: 2026-05-22（2024 年 3 月の活動を遡及してまとめたレポートです）

## 1. 概要

AB/Connect Working Group（AB/Connect WG）は、OpenID Connect 仕様群および OpenID Federation 系仕様を策定する OpenID Foundation 最古参の WG である。2024 年 3 月時点の共同議長は Nat Sakimura、Michael B. Jones、John Bradley の 3 名。当時、議事録は ML 公開アーカイブ（`openid-specs-ab`）にスレッドとして投稿され、Issue は Bitbucket（`bitbucket.org/openid/connect`）で管理されるという、伝統的な運用が継続していた。

2024 年 3 月は、AB/Connect WG にとって 「OpenID for Verifiable Credential Issuance (OID4VCI) 1.0 第 1 次 Implementer's Draft の投票プロセスが正式に開始された月」 であると同時に、 「OpenID Federation 1.0 の Editor's Draft 整理が Bitbucket Issue 起票として最も集中した月」 にあたる。月内に投稿された `openid-specs-ab` ML メッセージは合計 27 通で、Federation Editor の Vladimir Dzhuvinov を中心とした Bitbucket Issue #2123〜#2138 の連続起票（編集者自身による draft 33 ベースの規範整理が中心）、3/7 の Spec Call（IETF 119 直前の整理コール）、3/11 投票通知、3/25 投票開始、3/19 と 3/26 の Pacific Call キャンセル、3/31 の Federation certification tests 初版提案、が中心となった。

当月の主要トピックは大きく次の 5 系統に整理できる。

- **OID4VCI 1.0 ID1 投票プロセスの正式開始 (2024-03-11 通知, 3/18 early voting, 3/25 - 4/1 official voting)**: Marie Jordan（OpenID Foundation Secretary）から Notice of Vote が ML に投稿され、members poll #328 が告知された。45 日の Public Review 期間（2/8 - 3/25）の終了に合わせて投票期間が組まれた
- **OpenID Federation 1.0 Bitbucket Issue 集中起票 (#2123〜#2138, 16 件)**: Vladimir Dzhuvinov を筆頭に Federation Editor 陣（Mike Jones、Roland Hedberg）が editorial・規範両面で集中的に整理 Issue を起票。draft 33 段階の課題出しが 3 月内で一気に進行
- **Native SSO for Mobile Apps draft 06 公開 (2024-03-08, George Fletcher)**: PR #702（`native_sso_support` メタデータ追加）レビューを経て Work Group Draft 06 として公開
- **3/7 Spec Call による IETF 119 (3/16-22, Brisbane) 直前整理**: Mike Jones の Fully-Specified Algorithms、Joseph Heenan の Client Attestation、Tobias Looker の Status Lists、George Fletcher の Transaction Tokens / First-Party Apps / Identity Chaining（Cross-Domain Authorization へリブランド検討）等の関連仕様情報を WG 内で共有
- **Federation Certification Tests の素案投稿 (2024-03-31, Mike Jones)**: Italy 配下の既存 OpenID Federation deployment から 791 件のテストケースを抽出し、Federation 汎用テストとして 60 件を「Yes」、7 件を「Conditional」と Mike Jones が一次分類。OAuth Security Workshop 2024（Rome、4/9-12）直前の認証チーム face-to-face 会合に向けた事前布石

3 月後半は IETF 119（3/16-22、Brisbane）と重なり、3/19 火曜の AB/Connect WG Pacific Call が「Cancelling due to IETF」を理由に取消、3/26 の Pacific Call も「議長陣が今週は不在のためキャンセル。OID4VCI Implementer's Draft への投票を忘れないように」との理由で取消となった。したがって、定例コールとして公開議事録が残ったのは **3/7 木曜 OpenID Connect Spec Call の 1 本のみ** という、構造的にコール機会が少ない月であった。

## 2. 公開された仕様・ドラフト改訂

3 月最大の節目は、OID4VCI 1.0 を第 1 次 Implementer's Draft (ID1) として承認するための **正式投票プロセスの開始** である。Marie Jordan（OpenID Foundation Secretary）が [ML #010273](https://lists.openid.net/pipermail/openid-specs-ab/2024-March/010273.html)（2024-03-11）として Notice of Vote を投稿した。

- **Public Review 期間**: 2024-02-08 〜 2024-03-25（45 日間）
- **Early Voting 開始**: 2024-03-18（Public Review 終了前にレビュー完了したメンバー向け）
- **Official Voting 期間**: 2024-03-25 〜 2024-04-01（7 日間）
- **投票場所**: [openid.net/foundation/members/polls/328](https://openid.net/foundation/members/polls/328)
- **位置づけ**: OID4VCI が「Verifiable Credentials の発行プロトコル」として OpenID Foundation の正式な安定版（Implementer's Draft）に到達する最初のマイルストーン候補

当時 OID4VCI は AB/Connect WG の SIOP/DCP サブグループの成果物として運営されており（独立した Digital Credentials Protocols WG への分離は 2024-07）、本通知は AB/Connect WG ML（`openid-specs-ab`）と Digital Credentials Protocols WG ML の両方を宛先に含む扱いで送付された。

なお、3/26 火曜の AB/Connect WG Pacific Call 取消通知（[ML #010282](https://lists.openid.net/pipermail/openid-specs-ab/2024-March/010282.html)）でも Nat Sakimura は「Please do not forget to cast your vote for the implementer's draft of Verifiable Credential Issuance.」と投票完了を会員に呼びかけており、月後半の WG 関心が投票成立（クォーラム充足）に向いていたことが伺える。

### OpenID Connect Native SSO for Mobile Apps 1.0 Work Group Draft 06 公開 (2024-03-08)

3 月 8 日、George Fletcher が [ML #010271](https://lists.openid.net/pipermail/openid-specs-ab/2024-March/010271.html) で OpenID Connect Native SSO for Mobile Apps 1.0 Work Group Draft 06 の公開を通知した。先行する PR #702（`native_sso_support` メタデータ追加）は Vladimir Dzhuvinov によるレビューコメント（[ML #010259](https://lists.openid.net/pipermail/openid-specs-ab/2024-March/010259.html)、3/1）を経てマージされており、3/7 Spec Call 議事録では PR #702 が承認後マージ済みとして報告されている。

- **追加仕様要素**: `native_sso_support` メタデータパラメータ
- **目的**: 同一の開発者（同一 device instance）から提供されるネイティブアプリ間で認証状態を共有するというネイティブアプリ SSO のユースケースを明示的にサポート

### Initial Federation Certification Tests 素案投稿 (2024-03-31, Mike Jones)

3 月最終日、Mike Jones は [ML #010285](https://lists.openid.net/pipermail/openid-specs-ab/2024-March/010285.html) として **OpenID Federation 向け certification tests の初版素案** を投稿した。

- **元データ**: Italy 配下の既存 OpenID Federation deployment が保有していた 791 件のテストケース
- **絞り込み**: OpenID Connect 固有テストと extension entity type 固有テストを除外し 212 件に縮小
- **一次分類結果**:
  - 60 件: Federation 汎用機能テスト（"Yes" マーキング、無条件に Federation Certification の候補）
  - 7 件: optional 機能の条件付テスト（"Conditional"）
  - 残り: 追加評価が必要（"?"）、または Italian-specific（"No"）
- **提案**: 4/9-12 の OAuth Security Workshop 2024（Rome）開催直前に certification team の face-to-face 会合を持ち、その agenda に Federation Certification を含める
- **WG への呼びかけ**: マーキング済みスプレッドシートを ML 添付し、コミュニティに review と feedback を依頼

この素案投稿は、Federation 1.0 を将来 Final 化する前提条件として「適合性試験スイートの整備」が必要であり、その出発点として **既存実 deployment のテストを reuse する** という方針を示した点で重要である。

## 4. メーリングリストの主要スレッド

3 月の `openid-specs-ab` ML には合計 27 通の投稿があった。Bitbucket Issue クロスポスト 16 件、議事録／キャンセル通知 5 件、Notice of Vote 1 件、技術投稿 5 件という分布である。技術的に重要な 5 本を取り上げる。

### [Issue #2123: Federation principles in Introduction](https://lists.openid.net/pipermail/openid-specs-ab/2024-March/010262.html) - 2024-03-01 起票（Mike Jones）

Mike Jones による「フェデレーションの基本原理を Introduction に明文化する」提案。先行する Issue #2122 の議論を踏まえ、Federation 仕様の Introduction に次の 2 原理を加えるべきと主張。

- **相互合意の原理（Mutual Agreement）**: 「エンティティがフェデレーションに加入するとき、フェデレーションが定めるルールを受け入れ遵守しなければならない。同時に、フェデレーションは予測可能な振る舞いを示し、フェデレーションルールに従わなければならない」
- **個別エンティティ視点の原理（Individual Entity Perspective、cornerstone）**: 「各エンティティの視点が意味を持つ。中間エンティティ（intermediary）は、superior が定義する範囲をさらに絞り込む形で subordinate の metadata を制限できる。この能力は仕様上保全されなければならない」

本 Issue は「Federation 1.0 がなぜそのように設計されているのか」という設計哲学を仕様に書き込む試みで、Editor's Draft の後の編集で取り込まれた。

### [Issue #2124: Entity type constraint regarding intermediate entities](https://lists.openid.net/pipermail/openid-specs-ab/2024-March/010263.html) - 2024-03-03 起票（Vladimir Dzhuvinov）

現行仕様の `leaf_entity_types` 制約は「leaf がどの entity type（例: `openid_relying_party`）を assume できるか」のみを制御対象としていた。しかし、intermediate entity も `federation_entity` 以外の role を assume できるケースがあり、現行仕様ではその場合の制約表現ができない。

Vladimir Dzhuvinov の提案: **`leaf_entity_types` を `entity_types` にリネームし、対象を leaf に限らず任意の Subordinate に一般化する**。これにより federation authority が trust hierarchy 全域に対して entity type 制約を一貫適用できるようになる。

本 Issue は draft 34（4/4 公開）以降の制約モデル整理の出発点となった。

### [Issue #2132: Explicit client registration for OAuth clients](https://lists.openid.net/pipermail/openid-specs-ab/2024-March/010276.html) - 2024-03-15 起票（Vladimir Dzhuvinov）

現行仕様の Explicit Client Registration（Section 12.2.2.1）は「Registered RP metadata under the `openid_relying_party` Entity Type Identifier」のみに制限されており、Plain OAuth client（OIDC ではない素の OAuth 2.0 client）が同じ仕組みで registration できない。

Vladimir Dzhuvinov の提案: **`openid_relying_party` に加え、`oauth_client` を Explicit Client Registration の対象 entity type に追加する**。これにより OAuth/OIDC を跨ぐ federated registration 相互運用性が改善する。

本 Issue は同日起票された #2133（`jwks` claim 要件の Section 3.5.10 と Section 12.2.2.1 間の矛盾整理）と一対の編集系列を成し、Explicit Client Registration 機構全体の見直しを促した。

### [Issue #2135: Metadata policy - space-separated list exception narrowing](https://lists.openid.net/pipermail/openid-specs-ab/2024-March/010280.html) - 2024-03-20 起票（Vladimir Dzhuvinov）

現行 draft 33 仕様（Section 6.1.1-9）は「space-separated list of strings として定義された metadata パラメータは、metadata policy の `subset_of` / `superset_of` / `default` 演算子では JSON array とみなす」という一般化された例外を定めていた。

Vladimir Dzhuvinov の指摘:

- この一般化された例外は危険である。なぜなら Federation library が個別 metadata パラメータの内部構文を知らずに metadata を処理した場合、`metadata_policy` 演算の決定性が損なわれ得るためである
- 提案: **例外を `oauth_client` の `scope` パラメータ（RFC 7591 由来）一つに限定する**
- 教訓化: 今後新規 Federation 仕様では「space-separated list」を新規 metadata に採用しない方針を明示すべき

本 Issue は「正しい設計」と「過去の RFC 7591 互換性」のトレードオフを論点とし、後の Federation draft 35 〜 36 で実装方針が定まる議論の発端となった。

### [Contribution: query syntax proposal](https://lists.openid.net/pipermail/openid-specs-ab/2024-March/010267.html) - 2024-03-05 投稿（Oliver Terbu）

Oliver Terbu（当時 MATTR 所属）が「Format-specific identity credential query syntax (OID4VC)」と題する PDF 文書を AB/Connect WG と Digital Credentials Protocols WG の両方に正式 contribution として提出。

- **対象**: OID4VC 系（OID4VP を中心とした credential 要求側プロトコル）における format-specific な query syntax
- **形式**: ML 投稿本文は短いカバーメール、技術詳細は約 129 KB の PDF 添付に集約
- **位置づけ**: 本 contribution は credential 要求側の表現力（特に SD-JWT VC や mdoc など複数 credential format を混在させたいケース）強化の素材として WG に投入された

本 contribution はその後 OID4VP の query syntax 議論および後の Digital Credentials Query Language（DCQL）系の議論の遠因として位置付けられる。

## 5. GitHub 上の議論

2024 年 3 月時点では、AB/Connect WG の Issue Tracker は依然として **Bitbucket（`bitbucket.org/openid/connect`）** で運用されていた。GitHub 検索クエリ `is:issue created:2024-03-01..2024-03-31` および `is:pr created:2024-03-01..2024-03-31` を `openid/connect` および `openid/federation` の両リポジトリに対して実行した結果、いずれも実質ゼロであり、3 月の議論実体は § 2 と § 4 で扱った Bitbucket Issue #2123 〜 #2138 のクロスポストに集約される。

唯一 GitHub 上で動きが確認できるのは Native SSO 関連の作業で、`openid/native-sso`（当時の作業リポジトリ）に対する PR #702（`native_sso_support` メタデータ追加）が 3/7 Spec Call までにマージされた。同 PR は当 WG が Bitbucket 中心運用から GitHub への移行を将来的に検討するうえでも、AB/Connect WG 配下で「GitHub 上で完結する PR レビュー → マージ → draft 公開」のフローを実証した数少ない例となる。

Bitbucket Cloud は SPA で WebFetch から本文を直接取得できないため、本レポートでは Bitbucket Issue の本文を ML へのクロスポスト経由で再構成した。これは AB/Connect WG の伝統的運用形態を所与とする限り、3 月の議論を一次情報レベルで追える唯一の経路である。
