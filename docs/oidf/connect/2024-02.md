# OpenID Foundation AB/Connect WG 活動レポート (2024年2月)

> 執筆日: 2026-05-22（2024 年 2 月の活動を遡及してまとめたレポートです）

## 1. 概要

AB/Connect Working Group（AB/Connect WG）は、OpenID Connect 仕様群および OpenID Federation 系仕様を策定する OpenID Foundation 最古参の WG である。2024 年 2 月時点の共同議長は Nat Sakimura、Michael B. Jones、John Bradley の 3 名。当時、議事録は ML 公開アーカイブ（`openid-specs-ab`）にスレッドとして投稿され、Issue は Bitbucket（`bitbucket.org/openid/connect`）で管理されるという運用が継続していた。

2024 年 2 月は AB/Connect WG にとって、**「OpenID for Verifiable Credential Issuance (OID4VCI) 1.0 第 1 次 Implementer's Draft の Public Review が開始された月」** であると同時に、**「OpenID Federation 1.0 draft 33 が Stefan Santesson の Swedish Federation 実装レビューを受けて公開された月」** にあたる。月内に投稿された `openid-specs-ab` ML メッセージは合計 35 通（#010220 〜 #010258、欠番 #010234・#010236・#010237・#010238 あり）で、Bitbucket Issue #2111〜#2122 の 12 件起票、定例コール 5 本（2/5、2/8、2/15 SIOP/DCP、2/21 DCP、2/22、2/26）と 2 本のキャンセル（2/19 Presidents Day、SIOP/DCP の 2/29 想定回相当）、Public Review 通知 1 件、Federation draft 33 公開通知 1 件、Native SSO PR #702 提出 1 件、技術投稿 4 件という構成である。

当月の主要トピックは大きく次の 5 系統に整理できる。

- **OID4VCI 1.0 第 1 次 Implementer's Draft の Public Review 開始 (2024-02-08)**: OpenID Foundation が 45 日間（2/8 〜 3/24）の Public Review を正式アナウンス。投票期間は 3/25 〜 4/1 と予告。Michael Jones が ML #010233 でコミュニティに告知
- **OpenID Federation 1.0 draft 33 公開 (2024-02-23, Michael Jones)**: draft 32 で「Subordinate Statement」「`metadata_policy_crit`（旧 `policy_language_crit`）」へ用語統一した流れを引き継ぎ、`metadata_policy_crit` の Subordinate Statement 限定化、authorization signed request object JWT の取扱い修正、Trust Mark の独立節昇格、General-Purpose JWT Claims 節追加、`private_key_jwt` を federation endpoint のデフォルト client authentication とする方針整理などを取り込んだ
- **Native SSO for Mobile Apps の論点整理と PR #702 提出 (2024-02-26, George Fletcher)**: Nat Sakimura が `device_secret` の命名適切性と複数ネイティブアプリ間の同一ユーザー保証の有無を問い、George Fletcher が IIW セッションでの命名経緯と「同一 device instance を同一ユーザーの代理証明として扱う」設計意図を回答。Issue #2101（既存実装側の native SSO 制約の整理要望）に対応した PR #702（Bitbucket）が月末に提出され、3 月の draft 06 公開につながる
- **OpenID Connect: 認可エンドポイントへの POST の扱い (Issue #2115)**: Joseph Heenan が「POST to authorization endpoint」の WG 合意形成を要求。2/12 Spec Call で「OAuth 2 では MAY、3rd-party cookie 制約下では POST の有用性が薄い」「ただし FHIR では POST が必須」との認識を共有し、警告レベルの認証テスト追加と FHIR 用プロファイル切り出し方針を仮置き
- **OpenID Federation 拡張案 (sector identifier / metadata policy at Trust Anchor)**: Axel Nennker が telco federation 観点から sector identifier 導入を提起（Issue #2118 / ML #010247、#010248）、Stefan Santesson が Trust Anchor Entity Configuration に metadata_policy を許容する Issue #2122 を月末に起票。いずれも 3 月以降の Federation 1.0 整理に向けたシードとなった

2 月の定例運用は概ね通常通り稼働し、3/16-22 の IETF 119 を前に各仕様の状況確認が活発に行われた月であった。

## 2. 公開された仕様・ドラフト改訂

### OpenID for Verifiable Credential Issuance 1.0 第 1 次 Implementer's Draft - Public Review 開始 (2024-02-08)

2 月最大の節目は、OID4VCI 1.0 を第 1 次 Implementer's Draft (ID1) として承認するための **45 日間の Public Review 開始** である。OpenID Foundation が [公式アナウンス](https://openid.net/review-of-proposed-implementers-draft-of-openid-for-verifiable-credential-issuance/) を 2024-02-08 に公開し、同日に Michael Jones が [ML #010233](https://lists.openid.net/pipermail/openid-specs-ab/2024-February/010233.html) で WG にも周知した。

- **Public Review 期間**: 2024-02-08 〜 2024-03-24（45 日間）
- **投票期間（予告）**: 2024-03-25 〜 2024-04-01（7 日間）
- **位置づけ**: OID4VCI が「Verifiable Credentials の発行プロトコル」として OpenID Foundation の正式な安定版（Implementer's Draft）に到達する最初のマイルストーン候補
- **当時の WG 帰属**: OID4VCI は AB/Connect WG の SIOP/DCP サブグループの成果物として運営されており（独立した Digital Credentials Protocols WG への分離は 2024-07）、本 Public Review は `openid-specs-ab` と Digital Credentials Protocols 系 ML の双方を対象に告知された

Michael Jones は ML #010233 で短く「公式ページのリンク」と「関係者への祝意」のみを記したが、本通知は後続の 3 月 Notice of Vote（#010273）へ直結する事務手続きの起点として 2 月の最重要マイルストーンとなった。

### OpenID Federation 1.0 draft 33 公開 (2024-02-23, Michael Jones)

Michael Jones は 2024-02-23、[ML #010254](https://lists.openid.net/pipermail/openid-specs-ab/2024-February/010254.html) として OpenID Federation 1.0 draft 33 の公開を通知した。

draft 33 の主要な変更点（同 ML 投稿および [self-issued.info 2/23 投稿](https://self-issued.info/?p=2417) より）:

- **`metadata_policy_crit` の Subordinate Statement 限定化**: 「`metadata_policy_crit` claim MAY only appear in Subordinate Statements」とし、trust chain 全体のポリシー解釈にまたがって適用される旨を明文化（Issue #2111 への対応）
- **Authorization signed request object JWT 取扱いの修正**
- **Trust Marks 節の昇格**: 仕様内の独立した top-level セクションへ Trust Marks を移動
- **General-Purpose JWT Claims 節の新設**: 仕様内で多数の JWT 種別に共通する claim を整理
- **`private_key_jwt` を federation endpoint のデフォルト client authentication として明記**（Issue #2113 / #2114 への対応）
- **制約定義・エンドポイント仕様の整理**

draft 32 ですでに導入されていた変更（用語を「Subordinate Statement」に統一、`policy_language_crit` を `metadata_policy_crit` にリネーム）の延長線上で、draft 33 は **「Swedish Federation deployment テストにおける Stefan Santesson の包括レビュー」** を取り込んだ整理回として位置付けられる。Mike Jones は ML 投稿末尾で Stefan Santesson の貢献を明示的に謝辞している。

なお同月末（2/29）に Stefan Santesson が起票した Issue #2122（Trust Anchor Entity Configuration に metadata policy を許容）は draft 33 にはまだ取り込まれておらず、draft 34 以降の議論に持ち越された。

2 月の `openid-specs-ab` ML には合計 35 通の投稿があった。技術的に重要な 5 本を取り上げる。

### [Two questions on Native SSO draft](https://lists.openid.net/pipermail/openid-specs-ab/2024-February/010226.html) - 2024-02-08 開始（Nat Sakimura）

Nat Sakimura が Native SSO for Mobile Apps 1.0 ドラフトについて 2 点を George Fletcher に質問。

- **命名の妥当性**: 「token endpoint から返される token」を `device_secret` と呼ぶのは適切か。`device_token` のほうが適切ではないか
- **ユーザー同一性保証**: Native App 1 と Native App 2 のユーザーが同一であることを保証する仕組みはあるか

George Fletcher の回答（[#010227](https://lists.openid.net/pipermail/openid-specs-ab/2024-February/010227.html)、2024-02-08）:

- 命名は IIW セッションで議論した経緯があり、`device_secret` は「authorization server が発行し、device と server の間で confidential に保持される token」を表現している。既デプロイ実装数を踏まえると今からの名称変更は望ましくない
- ユーザー同一性については仕様で明示的な検証はしていない。SSO フローは複数アプリ間でユーザー同一性を verify しないのが通常であり、「同一 device instance を使う事実」を「同一ユーザーの十分な証明」とみなす設計。追加認証（biometric 等）はアプリ側で個別実装可能。要望があれば security considerations を強化する

このスレッドは Native SSO の設計哲学を ML 上で公にする契機となり、3/7 Spec Call での draft 06 公開判断、3/8 公開（#010271）に直結した。

### [Issue #2111: Location and scope of metadata_policy_crit](https://lists.openid.net/pipermail/openid-specs-ab/2024-February/010220.html) - 2024-02-01 起票（Vladimir Dzhuvinov）

Vladimir Dzhuvinov による Federation 仕様の 2 点問題提起。

- **配置の曖昧性**: `metadata_policy_crit` claim が Entity Configurations と Subordinate Statements のどちらに出現可能か仕様上不明。`metadata_policy` が Subordinate Statement のみに出現する以上、`metadata_policy_crit` も Subordinate Statement のみに限定するのが論理的と主張
- **適用スコープの曖昧性**: `metadata_policy_crit` が `"lte"` 等の critical 拡張演算子を列挙する場合、その適用範囲が「同一 Subordinate Statement 内の `metadata_policy`」か「Trust Chain 上のすべての subordinate `metadata_policy`」か曖昧

本 Issue の指摘は draft 33（2/23 公開）に取り込まれ、「`metadata_policy_crit` MAY only appear in Subordinate Statements」かつ trust chain 全体のポリシー解釈に対して適用される、という整理に至った。

### [Issue #2115: POST to authorization endpoint](https://lists.openid.net/pipermail/openid-specs-ab/2024-February/010228.html) - 2024-02-08 起票（Joseph Heenan）

Joseph Heenan が前月（2024-01）からの議論を踏まえ、認可エンドポイントへの POST サポート要件について WG 合意形成を要求。論点は「認証テスト追加か、仕様改訂か」の二択。

2/12 Spec Call では:

- 「OAuth 2 では MAY」
- 「機能として大きな価値を加えていない」（複数参加者）
- 「実質的に有用ではない機能」

との発言が記録された。一方 2/8 Connect WG Call では「FHIR は POST を必須としている」という事実を踏まえ、警告レベルの認証テストと FHIR 用専用プロファイル切り出しが妥当との方向感が共有された。

本 Issue は 2 月中に最終合意に到達せず、3 月以降に持ち越された。

### [add security warning to implicit grant or deprecation in OIDC](https://lists.openid.net/pipermail/openid-specs-ab/2024-February/010244.html) - 2024-02-17 開始（Axel Nennker）

Axel Nennker（Deutsche Telekom）が OIDC における implicit grant flow の扱いを問題提起。

- IETF OAuth WG・OWASP の双方が implicit flow に対する警告を発している事実を引用（OWASP: "The implicit flow in OAuth only is deprecated, yet is still a viable solution within Open ID Connect (OIDC) to retrieve id_tokens."）
- 「OIDC 仕様が implicit flow の脅威評価と緩和策を本仕様内に明記していないのはなぜか」を問う
- 提案: implicit flow の脅威評価を core 仕様に取り込む、または implicit flow サポート自体を廃止する。実装ガイドのみで扱うのは不十分

本投稿は OIDC core 仕様の現代化（脅威モデルの最新化）を求める声として記録されたが、core 仕様改訂は当時の WG では低優先度に置かれていた論点であり、月内の追加返信はなかった。

### [sector identifier in openid federation](https://lists.openid.net/pipermail/openid-specs-ab/2024-February/010247.html) - 2024-02-20 開始（Axel Nennker、Issue #2118 と一対）

Axel Nennker が telco federation 観点から sector identifier を OpenID Federation に導入することの妥当性を問う投稿。

- OIDC が pairwise id とその計算方法を議論している現状を確認
- sector identifier は複数の party が同一の Pairwise Pseudonymous Identifier (PPID) を共有する仕組みを与える
- federation 内の entity 群は当然「ユーザーに対する共通 PPID」を望むはず
- 取り組むべき問い: (1) sector identifier を Federation 仕様に含めるべきか、(2) 個別に追加可能なので仕様内定義は不要か、(3) プライバシー影響はどうか
- 補足: 「globally unique」識別子では運用上問題があるという telco federation の事例を提示

本投稿と並行して同氏が Issue #2118 を起票し、2/22 Connect WG Call で議題化された。3 月以降の Federation 拡張議論のシードとして残った。

## 5. GitHub 上の議論

2024 年 2 月時点では、AB/Connect WG の Issue Tracker は依然として **Bitbucket（`bitbucket.org/openid/connect`）** で運用されており、GitHub 上の OpenID 配下リポジトリ（`openid/connect`、`openid/federation`、`openid/native-sso`、`openid/OID4VCI` 等）の Issue / PR 活動は限定的だった。Bitbucket Cloud は SPA レンダリングのため WebFetch から本文を直接取得できないため、本レポートでは Bitbucket Issue の本文を ML へのクロスポスト経由で再構成した（§ 2 および § 4 に統合）。
