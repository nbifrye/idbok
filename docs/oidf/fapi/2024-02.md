# OpenID Foundation FAPI WG 活動レポート (2024年2月)

> 執筆日: 2026-05-22（2024 年 2 月の活動を約 2 年遡って再構成した遡及レポートです）

## 1. 概要

FAPI (Financial-grade API) Working Group は、金融 API をはじめとする高保証用途向けに OAuth 2.0 / OpenID Connect のプロファイルを策定する OpenID Foundation のワーキンググループである。FAPI は単一仕様の名称ではなく、Baseline / Advanced（FAPI 1）と Security Profile / Attacker Model（FAPI 2）からなる仕様ファミリーで、UK Open Banking、Brazil Open Finance、Australia の CDR、Saudi Arabia Open Banking など各国の金融 API 標準の参照ベースとして採用されてきた。2024 年 2 月時点の共同議長は Nat Sakimura (NAT Consulting)、Dave Tonge (Moneyhub)、Dima Postnikov、Anoop Saxena (Intuit) の 4 名。エディタ作業は Daniel Fett (Authlete)、Dave Tonge、Joseph Heenan (Authlete) を中心に進められていた。

2024 年 2 月の FAPI WG は、**3 月以降の「Issue 集中起票 + Final 化前準備」フェーズに入る直前の地ならし月** にあたる。月内の ML 投稿は 15 件（メッセージ番号 [#003052〜#003066](https://lists.openid.net/pipermail/openid-specs-fapi/2024-February/)）で、3 月の 19 件・4 月の 23 件・5 月の 29 件と比較するとやや控えめだが、**Atlantic コール 2 回（2/7、2/14、2/28 はリマインダーのみで月内開催、2/28 は 2.5 時間後開催）が ML 上で確認** でき、定例運用は安定して継続していた。

月内の主要な動きは次の 3 系統に整理できる。

第 1 に、**FAPI 2.0 Security Profile / Attacker Model に対する Issue 起票が 4 件（#639 / #674 / #675 / #676）** あり、Nat Sakimura、Joseph Heenan、Brian Campbell、Ralph Bragg と編集者層・実装者層の多様なメンバーが分担した。とくに 2/14 の Atlantic コール直前に Dave Tonge が [Issue Summary for FAPI 2 (ML #003060)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-February/003060.html) を投函し、FAPI 2.0 Security Profile と Attacker Model に残存する **13 件以上の未解決 Issue（#638 / #642 / #646 / #651 / #652 / #653 / #656 / #659 / #660 / #665 / #670 / #672 / #674）** を「WG コール上で議論を要するもの」と「editorial にクローズ可能なもの」に分類してコール議題化したことが、この月の WG 内整備プロセスの中心である。3 月の #677〜#688 集中起票（12 件）はこの 2 月の整理がベースになる流れである。

第 2 に、**Anders Rundgren（独立系コントリビュータ）による Open Banking / Open Finance の architectural critique スレッドが 2 月の前半・後半に 2 本走った**。2/5 開始の [EY View of Open Banking (ML #003052)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-February/003052.html) は、Ernst & Young が発表した Open Banking 関連分析を題材に Rundgren が「APIs / モジュラーアーキテクチャ / マイクロサービス志向」のビジョン共有を確認したうえで「PoC が欠けている」と問題提起したスレッドで、**Gail Hodges (OIDF Executive Director) が 2/5 20:53 UTC に [ML #003053](https://lists.openid.net/pipermail/openid-specs-fapi/2024-February/003053.html) で「I think it will be useful for consultants like E&Y to be clear on OIDF / FAPI role when they are advising clients」と返信** し、EY の lead writer に直接コンタクトしたことも併記した点が記録上重要である。Hodges が public list 上で「コンサルティングファーム経由の FAPI 認知向上」を具体的アクションとして表明した投稿はこの月のものが代表的である。2/19 開始の [Berlin Group openFinance - Workplan 2024 (ML #003062)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-February/003062.html) では、Rundgren が Berlin Group の 2024 Workplan を取り上げ、Swish（スウェーデン）・BLIK（ポーランド）・Bizum（スペイン）・TWINT（スイス）といったウォレット決済が Open Banking 仕様の外で運用されている現状を指摘し、ウォレット統合論点をビデオ会議形式で構造化議論することを提案した。

## 2. 公開された仕様・ドラフト改訂

2024 年 2 月内に FAPI 2.0 Security Profile / Attacker Model / Message Signing / CIBA の新しい公開ドラフト版・Implementer's Draft・Final ドラフトは公開されていない。2 月の規範作業は **未解決 Issue を仕分けして 2/14 Atlantic コールでの議論議題に整理し、3 月以降の Issue 集中起票・WGLC 起動に向けた地ならしを行うフェーズ** であり、ドラフト本体の版番号変更を伴わなかった。月内に ML 上で展開された主要な技術論点は以下のとおり。

### 2-2. Issue #639: FAPI 2.0 Title Change - Part 1, Part 2 への番号付与（Nat Sakimura、2/5）

[ML #003057 (Nat Sakimura, 2024-02-05)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-February/003057.html) は、Sakimura が **ISO 中央事務局との協議経験を踏まえて FAPI 2.0 仕様群にパート番号を付与する構造改革を提案** した投稿である。論点は以下のとおり。

- ISO 中央事務局は OpenID Connect 仕様に対しても「パート番号を付ける」要請を行っており、ISO PAS ルートで標準化を進める場合には Multi-part 構造化が事実上の前提となる
- 提案する構成: **Part 1: Attacker Model / Part 2: Security Profile** から出発し、後から追加拡張可能とする
- **CIBA（Client Initiated Backchannel Authentication）も同じスイートの一部として番号付与すべきか** を WG に問いかけ

Sakimura は OpenID Connect Core を ISO PAS で ISO/IEC 26131 として標準化した経験を直接持つ立場で、FAPI 2.0 を将来 ISO PAS ルートに乗せる際に「Multi-part 構造」が必要になることを WG に提示した格好である。後の 3 月 15 日 Gail Hodges による [ISO PAS リード人員公募 (ML #003077)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-March/003077.html) を約 5 週間後に控えた時点の伏線的提案として位置づけられる。Message Signing や Dynamic Client Registration（後の FAPI 2 family 拡張）が連動して Part 番号体系に組み込まれる構想も示された。

### 2-3. Issue #674: OP conformance tests における nonce 長（Joseph Heenan、2/5）

[ML #003058 (Joseph Heenan, 2024-02-12)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-February/003058.html) は、**OIDF Certification Suite 責任者の Heenan が実装テスト現場の不整合を直接 Issue 化した** 投稿である。Heenan は WG 内で実装相互運用の異常を最も早く検知できる立場にある。

問題の構造:

- 現在の **FAPI1 / FAPI2 OP テストは 10 文字の nonce のみを試行** する
- 認証取得済みクライアントが **43 文字までの nonce** を実装で使用していることが Suite 側で確認されている
- 現在の **RP テストは「43 文字超の nonce」に対して warning（fail ではない）** を出す運用
- 提案: OP が 43 文字 nonce に対応することを要件化し、OP テスト・RP テスト両方の一貫性を確保

参照されているチケット番号は GitLab `#1217`（認証取得済みクライアントの nonce 長データ）と `#1307`（43 文字 nonce 確認の追加追跡）であり、Conformance Suite の運用ログ起点の議題提起である。本 Issue は 2/14 Tonge の Issue Summary でも「Needs WG discussion」に分類されており、コール議題として明示的に俎上に乗せられた。

### 2-4. Issue #675: HTTP Message Signatures / Digest Fields の参照更新（Brian Campbell、2/5）

[ML #003061 (Brian Campbell, 2024-02-14 20:47 UTC)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-February/003061.html) は、**HTTP Message Signatures が RFC 9421 として、Digest Fields が RFC 9530 として 2024 年 2 月に正式刊行された** ことを受けて、FAPI 2.0 Message Signing 仕様内でドラフト参照していた両仕様への参照を正式 RFC 番号に更新するよう求めた editorial 修正提案である。Campbell は Ping Identity のディスティングイッシュド・エンジニアとして HTTP Message Signatures 仕様策定にも IETF 側で深く関与しており、刊行直後の最も鮮度高いタイミングで FAPI Message Signing 側の参照更新を提起した形である。

### 2-5. Issue #676: NOTE 2 における Clause 参照訂正（Ralph Bragg、2/23）

[ML #003065 (Ralph Bragg, 2024-02-23 21:25 UTC)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-February/003065.html) は、Raidiam の Bragg が **NOTE 2 の Clause 参照誤りを editorial 修正として提起** した投稿である。修正対象は次の規範文言を含む NOTE 2:

> shall not use refresh token rotation unless, in the case a response with a new refresh token is not received and stored by the client, retrying the request will succeed

現状の NOTE 2 が「Clause 9 の要件に従う」と記述しているが、Bragg は **正しい参照は Clause 10** であると指摘した。これは Refresh Token Rotation 利用時の「新トークン応答が未受信・未保存の状態でクライアントが再試行した場合に成功させる」運用要件と、Clause 10（通常 Refresh Token に関する細則）との対応関係に関係する。Bragg は Raidiam として複数 Open Banking エコシステム（特に UK・Brazil）の認証テスト基盤運用に従事する立場で、テキストの参照不整合が conformance テスト結果に直接影響することを最も具体的に把握できる位置にある。

### 2-6. Grant Management の formal security analysis（Marcus Almgren、2/7 Atlantic コール）

[ML #003056 (Marcus Almgren, 2024-02-07 13:24 UTC)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-February/003056.html) は、Almgren が **「a proposed formal security analysis of Grant Management のトピックを Atlantic コールで簡単に取り上げたい」** と当日アジェンダ追加を依頼した短い投稿である。Grant Management for OAuth 2.0 は FAPI 2 family の add-on 仕様（Dima Postnikov が Medium で実装ガイドを発信していたファイングレード認可仕様）であり、Stuttgart 大学グループ（Daniel Fett・Pedram Hosseyni・Tim Würtele）による FAPI 2.0 系の formal security analysis が 2022 年に第一弾を完了したのち、Message Signing / DCR / DCM / FAPI-CIBA 系を含む拡張版へと作業が継続されていた流れの中での提起と推察される。本 ML 投稿は Atlantic コール議題への追加依頼であって、formal analysis 文書の WG レビュー版そのものが 2 月に公開されたわけではない。

## 3. ミーティングと議論

FAPI WG は 2024 年 2 月時点で Atlantic コール（水曜 14:00 UTC、隔週運用）と Pacific コール（隔週 Friday / Wednesday、Asia-Pacific 帯）の 2 系統を運用していた。Bitbucket wiki 上の議事録ページ（[`FAPI_Meeting_Notes_2024-02-XX`](https://bitbucket.org/openid/fapi/wiki/browse/) 系統）は SPA レンダリングのため本記事執筆経路では本文を直接抽出できないが、ML 投稿のアジェンダ・リマインダー・事後報告から各コールの開催状況と議題を再構成する。

### EY View of Open Banking — 2/5 開始 (Anders Rundgren / Gail Hodges)

[ML #003052 (Rundgren, 2/5)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-February/003052.html) → [ML #003053 (Hodges, 2/5)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-February/003053.html) → [ML #003054 (Rundgren, 2/6)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-February/003054.html) の 3 投稿スレッド。EY が公表した Open Banking 分析記事への Rundgren の反応に対し、**Gail Hodges (OIDF Executive Director) が「consultants like E&Y に OIDF / FAPI の役割を明確化してもらうことが有用」と public list 上で表明し、当該記事の lead writer に直接コンタクトしたことを併記** したことが本月最大の戦略的記録である。コンサルティングファーム経由での FAPI 認知向上という方針が、OIDF 上層部から WG ML へ具体的アクションとして表明されたタイミングとして残る（§2 / §6 参照）。Rundgren は 2/6 の返信で「提案アーキテクチャは OIDC / FAPI の廃止ではなく Open Banking の再構成」と明確化し、SD-JWT 経由の仮想ペイメントカード発行に OIDC 技術を活用する道筋を提示した。

### Berlin Group openFinance - Workplan 2024 — 2/19 開始 (Anders Rundgren / Nat Sakimura)

[ML #003062 (Rundgren, 2/19)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-February/003062.html) → [ML #003063 (Sakimura, 2/21)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-February/003063.html) の 2 投稿スレッド。Rundgren が Berlin Group の 2024 Workplan を取り上げ、以下を問題提起した。

- **「the current architecture excludes third-parties from contributing to the Open Banking ecosystem」**: Berlin Group の現行アーキテクチャがサードパーティ参入を排除している構造的問題
- **ウォレット連携の不在**: Berlin Group Workplan の Note 2.6（wallet integration）を参照し、Swish（スウェーデン）・BLIK（ポーランド）・Bizum（スペイン）・TWINT（スイス）といった主要ウォレット決済システムが Open Banking フレームワークと無関係に運用されている現状を例示
- **UK Open Banking Ltd. のウォレット統合ガイダンス未公開**
- **構造化議論の提案**: ウォレット統合を優先トピックとするビデオ討議

Sakimura の返信（2/21）は簡潔な謝意表明にとどまる。Rundgren のこのスレッドは、後の 3/4 EU Payment Wallet スレッド（[ML #003067〜#003069](https://lists.openid.net/pipermail/openid-specs-fapi/2024-March/003067.html)）に直接連続する論点群を 2 月時点で先取りした提起であり、本月の Open Banking architectural critique の代表的スレッドである。

## 5. Issue トラッカー上の動き

FAPI WG の Issue トラッカーは Bitbucket (`bitbucket.org/openid/fapi/issues`) で運用されている。Bitbucket Cloud は SPA レンダリングのため Issue 本文の直接取得経路は限定的だが、対応する ML 投稿から内容を把握できる。

2024 年 2 月に ML 上で起票・周知が確認できる Issue は **4 件（#639 / #674 / #675 / #676）** で、起票者と主題は以下のとおり。

- [Issue #639: FAPI 2.0 Title Change - Add Part 1, Part 2, etc...](https://bitbucket.org/openid/fapi/issues/639) — Nat Sakimura、2024-02-05。ISO 中央事務局協議を踏まえた Multi-part 構造化提案。CIBA の同スイート含有を WG に問いかけ
- [Issue #674: length of nonce tested in OP conformance tests](https://bitbucket.org/openid/fapi/issues/674) — Joseph Heenan、2024-02-05〜02-12。OP テストの 10 文字 nonce のみ試行を 43 文字対応要件化する提案。Conformance Suite 運用ログ起点
- [Issue #675: update refs for HTTP Message Signatures & Digest Fields](https://bitbucket.org/openid/fapi/issues/675) — Brian Campbell、2024-02-14。RFC 9421 / RFC 9530 正式刊行を受けた参照更新提案
- [Issue #676: Incorrect reference in note2](https://bitbucket.org/openid/fapi/issues/676) — Ralph Bragg、2024-02-23。NOTE 2 の Clause 9 → Clause 10 参照訂正。Refresh Token Rotation 関連

4 件の内訳は **編集論点 2 件（#675 / #676）、構造論点 1 件（#639）、相互運用性論点 1 件（#674）** で、起票者は WG 内の異なるロール（Sakimura は共同議長 / ISO 標準化経験者、Heenan は Conformance Suite 責任者、Campbell は IETF HTTP Message Signatures エディタ、Bragg は Open Banking エコシステム実装者）にきれいに分担されている。これは 2 月時点で WG メンバーの各層が **自分の専門領域に直接接続する論点を独立に Issue 化し** 、Tonge の Issue Summary がそれを集約する WG 運営パターンが機能していたことを示す。

加えて [Issue Summary for FAPI 2 (ML #003060)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-February/003060.html) によれば、本月の WG 内議論対象は新規 4 件に **既存の #638 / #642 / #646 / #651 / #652 / #653 / #656 / #659 / #660 / #665 / #670 / #672** を加えた合計 16 件以上に及び、Final 化前の正本テキストへ反映すべき論点が WG 内で蓄積していた。Tonge の仕分けに従い editorial 系は順次クローズに向かい、WG 議論要のものは 2/14・2/21・2/28 の Atlantic コール枠で扱われる流れになった。

GitHub `openid/fapi` リポジトリは Bitbucket の公開ミラー的位置付けで、編集ワークフローの主軸は引き続き Bitbucket 上の PR / Issue で運用されていた。

### OpenID Verifiable Credential Issuance Public Review 開始（2/8）

[Public Review Period for Proposed Implementer's Draft of OpenID for Verifiable Credential Issuance](https://openid.net/review-of-proposed-implementers-draft-of-openid-for-verifiable-credential-issuance/) が 2/8 に OIDF 公式から公示。OID4VCI 1.0 を Implementer's Draft 1 に昇格させるための 45 日間 Public Review（2/8〜3/24）、Early voting 3/18、Official voting 3/25〜4/1 のタイムラインで起動。AB/Connect WG 担当（後の 4/15 提案で DCP WG に移管）。FAPI WG の直接の所掌ではないが、Open Banking エコシステムが Wallet 連携を進める際の基盤仕様として後年関連性を持つ。

### OpenID Federation 1.0 - draft 33 公開（2/23）

Mike Jones の [self-issued.info 2024 年 2 月公開記事](https://self-issued.info/?m=202402) によれば、[OpenID Federation 1.0 - draft 33](https://openid.net/specs/openid-federation-1_0-33.html) が 2/23 公開。FAPI WG の直接の所掌ではないが、Open Finance Brazil・Swedish Federation 等が FAPI 仕様と組み合わせて Federation 仕様を採用しているため、後年 FAPI 採用エコシステムの Trust Chain 評価実装に関わる仕様基盤精緻化として位置付けられる。

### MWC Barcelona 2024（2/26〜2/29）

[MWC Barcelona 2024](https://www.gsma.com/mwc/) が Fira Barcelona Gran Via で 2/26〜2/29 開催。88,000 名以上が 200 ヶ国超から参加した世界最大級のモバイル通信業界カンファレンス。OIDF として MWC への公式参加・登壇に関する 2 月内の openid.net 公示は確認できないが、Open Banking と密接な関係を持つモバイル決済・ウォレット領域の業界動向を把握する観点で FAPI WG メンバーが現地参加していた可能性は十分にある。
