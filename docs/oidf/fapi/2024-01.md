# OpenID Foundation FAPI WG 活動レポート (2024 年 1 月)

> 執筆日: 2026-05-22（2024 年 1 月の活動を約 2 年 4 ヶ月遡って再構成した遡及レポートです）

## 1. 概要

FAPI (Financial-grade API) Working Group は、金融 API をはじめとする高保証用途向けに OAuth 2.0 / OpenID Connect のプロファイルを策定する OpenID Foundation のワーキンググループである。FAPI は単一仕様の名称ではなく、Baseline / Advanced（FAPI 1）と Security Profile / Attacker Model（FAPI 2）からなる仕様ファミリーで、UK Open Banking、Brazil Open Finance、Australia の CDR、Saudi Arabia Open Banking など各国の金融 API 標準の参照ベースとして採用されてきた。2024 年 1 月時点の共同議長は Nat Sakimura (NAT Consulting)、Dave Tonge (Moneyhub)、Dima Postnikov、Anoop Saxena (Intuit) の 4 名。エディタ作業は Daniel Fett (Authlete)、Dave Tonge、Joseph Heenan (Authlete) を中心に進められていた。

2024 年 1 月の FAPI WG は、**前年末（2023-12-29）に Nat Sakimura が OIDF を代表して提出した CFPB Rule 1033 (Personal Financial Data Rights) コメントレター**の直後にあたる月であり、米国 Open Banking 規制の議論で FAPI を「Standardized Communication Protocol」の事例として明示的に提示した直後の局面である。月内の ML 投稿は **50 件（メッセージ番号 [#003002〜#003051](https://lists.openid.net/pipermail/openid-specs-fapi/2024-January/)）** と、2024-02 の 15 件・2024-03 の 19 件・2024-04 の 23 件と比較してもひときわ多い。これは月内の **Issue 大量起票（#638〜#673 の合計 35 件超）** が ML に逐次通知されたためで、FAPI 2.0 Security Profile / Attacker Model の Final 化に向けた **論点棚卸しが本格化したフェーズ** である。

## 2. 公開された仕様・ドラフト改訂

2024 年 1 月内に FAPI 2.0 Security Profile / Attacker Model / Message Signing / CIBA の新しい公開ドラフト版・Implementer's Draft・Final ドラフトは公開されていない。1 月の規範作業は **Final 化前に正本テキストへ取り込むべき論点を Issue として網羅的に棚卸しするフェーズ** であり、ドラフト本体の版番号変更を伴わなかった。月内に ML 上で展開された主要な技術論点は以下のとおり。

### 2-1. FAPI 2.0 の多パート構造化提案（Sakimura、#639 / #640 / #655）

[ML #003007 (Sakimura, 2024-01-09)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-January/003007.html)、[ML #003008 (#640)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-January/003008.html)、[ML #003023 (#655)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-January/003023.html) は、Sakimura が **ISO 中央事務局との協議経験を踏まえて FAPI 2.0 仕様群の構造改革を一気に提示** した投稿群である。論点は以下のとおり。

- **Issue #639**: FAPI 2.0 を Part 1: Attacker Model / Part 2: Security Profile / Part 3: Message Signing / Part 4: Dynamic Client Registration の多パート構造に再編。CIBA を同スイートに含めるかを WG に問いかけ
- **Issue #640**: ISO Directives Part 2 準拠の章立てに整理（Foreword / Introduction / Warning / Notational conventions / Scope / Normative references / Terms / Symbols / Security goals / Attacker models / Attackers / Limitations の 8 章 + Annex 3 本）。Edmund Jay 担当
- **Issue #655**: Security Profile §5.1 の「aims to reach the security goals laid out in the Attacker Model」を「**shall fulfill** the security goals laid out in the Attacker Model」へ修正。Attacker Model 文書を規範参照として強制化

これらは Sakimura が OpenID Connect Core を ISO PAS で ISO/IEC 26131 として標準化した経験を直接持つ立場で、FAPI 2.0 を将来 ISO PAS ルートに乗せるための土台整備として一気に提示した格好である。2 月の Tonge による Issue Summary、3 月の Sakimura による Issue #677〜#688 集中起票、3/15 Gail Hodges による ISO PAS リード人員公募と続く流れの起点として位置づけられる。

### 2-2. ID Token Encryption の規範論点（Heenan、#659）と 1/17 コール議題化

[ML #003027 (Heenan, 2024-01-10)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-January/003027.html) は、**OIDF Certification Suite 責任者の Heenan が実装相互運用の不整合を Issue 化** した投稿である。問題の構造:

- FAPI 2 の特性比較表は「No encryption and no ID Tokens in the front channel」と記載
- しかし本文に id_token 暗号化を禁止する規範文言は存在しない
- 結果として **Conformance Tests は OP が暗号化 id_token を返すことを許容するが、Client 側が暗号化 id_token を処理できるかはテストしていない**
- 比較表と本文・テストの整合性を確保する必要

本論点は 1/17 Atlantic コールのドラフトアジェンダにも「ID Token Encryption」として明示的に第 5 議題内のサブ論点として配置されており（ML #003045）、コール内での議論対象として明確に俎上に乗せられた。

### 2-3. Mandatory MTLS の規範化（Heenan、#670）

[ML #003038 (Heenan, 2024-01-13)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-January/003038.html) は、**主要 4 エコシステム（ConnectID / Brazil Open Finance / UK Open Banking / CDR Australia）が一様に「全エンドポイント MTLS 必須」を採用していた実態** と仕様の乖離を Heenan が問題提起した投稿である。

- Sender-constrained access token と MTLS を併用する場合、仕様上 MTLS が必要なのは数エンドポイント（discovery / server JWKS / PAR 等）のみ
- 一方、各エコシステムは **`private_key_jwt` 認証と並行して MTLS を「Defence in depth」として全エンドポイントで強制**
- 結果として、エコシステムごとに別個の certification test variant を維持する必要が生じている
- 解決策: 仕様・Certification Tests の双方で「Mandatory MTLS」を Optional Configuration として明示し、テスト・ドキュメントの一元化を図る

本 Issue は Heenan が Conformance Suite 運営者として 4 エコシステムの相互運用テストを横断的に見ている立場で初めて整理可能な観察に基づいており、後の 2 月 Tonge Issue Summary でも「Needs WG discussion」に分類されて継続審議となる。

### 2-4. `require_pushed_authorization_requests` 明示要件化（Verstege、#666）

[ML #003034 (Mark Verstege, 2024-01-12)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-January/003034.html) は、Consumer Data Right (Australia) の Verstege が **RFC 9126 PAR の `require_pushed_authorization_requests` の既定値が `false` である点に着目**し、FAPI Security Profile §5.3.1.2 に「`require_pushed_authorization_requests` を `true` に設定することを明示要件化する」文言を追加すべきと提案した投稿である。PAR 必須化を運用上担保するため、Authorization Server Metadata 上で曖昧さを残さないようにする精緻化提案である。

### 2-5. 暗号アジリティ系: Ed25519 fully-specified identifier 対応（Skokan、#658）と PQC 議論（Rundgren）

[ML #003026 (Filip Skokan, 2024-01-09)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-January/003026.html) は、JOSE WG で策定中の **Ed25519 用 fully-specified JWS algorithm identifier** が確定した際に FAPI 2.0 がそれを許容できるよう、現行の明示列挙ベースの許容アルゴリズムリストを柔軟化する提案。後の "fully-specified algorithms for JOSE" 仕様（RFC 9783 系）に発展する論点系列の早期 Issue 化である。

これと別軸で、[ML #003043 (Anders Rundgren, 2024-01-17)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-January/003043.html) は **Post-Quantum Cryptography (PQC) 対応として JSON より CBOR が適切**との主張を行い、CBOR Deterministic Encoding (CDE) の IETF draft `draft-ietf-cbor-cde` を参照しつつ自身の Open Banking PoC を CBOR ベースで構築する意向を表明した。FAPI WG の正式議論対象とはならなかったが、PQC 移行を見据えた将来論点として ML 上に記録された。

### 2-6. Daniel Fett による Attacker Model 整備（#671 / #672、PR #455）

[ML #003039 (Fett, 2024-01-13, #671)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-January/003039.html) は、Stuttgart 大学グループの formal security analysis の結果を Attacker Model 文書に正式に参照として組み込み、attackers の番号付け空きを解消する提案。PR #455 で対応された。Fett は併せて [#672 (ML #003040)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-January/003040.html) で「Client / client」の大文字化不一貫性も指摘し、editorial 整備を進めた。

### 2-7. Joseph Heenan 自身の著者表記論点（#673）

[ML #003046 (Heenan, 2024-01-24)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-January/003046.html) は、Heenan が Sakimura・Fett・Tonge と相談した結果として **FAPI 2 SP / MS の著者として Heenan を追加するか** を WG として ticket 化したもの。エディタクレジット運用に関する手続的論点で、後年の Final 化版で正式に著者列に追加される流れにつながる。

### Question to clarify regarding FAPI-JARM — 1/16 開始 (Chamantha / Heenan)

[ML #003041 (Chamantha, 1/16)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-January/003041.html) → [ML #003042 (Heenan, 1/16)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-January/003042.html) の 2 投稿スレッド。Conformance Suite ユーザの Chamantha が、`request_object_without_exp_fails` 等のテストで「exp / nbf / scope が欠落する request object 内に置かれた `response_mode` の値を AS が信頼してよいか」と質問。Heenan は **「signature validation 失敗による完全無効」と「個別パラメータ欠損による invalid request」の区別** を明確化し、後者は valid JWT だが invalid request にあたるため `response_mode` を信頼する余地があると返答。AS が登録済み `redirect_uri` に redirect している時点で既に客船を信頼している点も補足した。最終的に Conformance Suite の formal issue として提起することを推奨。実装現場の細部質問が WG ML に直接持ち込まれ、Conformance Suite 責任者が即応する FAPI WG の応対文化を示すスレッド。

### Happy New Open Banking Architecture / Support for PQC / OBIE Wallet Interface — Anders Rundgren 連続投稿

[ML #003002 (1/1) Happy New Open Banking Architecture](https://lists.openid.net/pipermail/openid-specs-fapi/2024-January/003002.html) / [ML #003043 (1/17) Support for Post-Quantum Cryptography (PQC)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-January/003043.html) / [ML #003050 (1/28) OBIE Wallet Interface](https://lists.openid.net/pipermail/openid-specs-fapi/2024-January/003050.html) の 3 単発投稿。Rundgren は独立系コントリビュータとして月初・月中・月末に Open Banking architectural critique を投函している。

- **1/1**: Revised Open Banking Architecture 文書を共有し、CBOR-serialized Saturn を用いた PoC・リファレンス実装の構築意向。コア API は容易、admin インターフェースが課題と表明
- **1/17**: PQC が大量バイナリを要求するため CBOR が JSON より適切と主張。CBOR Deterministic Encoding (CDE) の IETF draft `draft-ietf-cbor-cde` を参照し、署名 CBOR の WebPKI ラボリンクを提示
- **1/28**: OBIE プラットフォームへの自身の「slashing」（厳しい批判）を認めつつ、ウォレット到来への応答計画の必要を主張。EU Digital Identity Wallet [GitHub Issue #104](https://github.com/eu-digital-identity-wallet/eudi-doc-architecture-and-reference-framework/issues/104) を参照し、モノリス refactoring が new security layer を導入する点で FAPI と関連すると説明

Rundgren の投稿系列は WG 公式の議論対象とはならないが、月末の OBIE Wallet Interface スレッドは 2 月の [Berlin Group openFinance Workplan 2024 (ML #003062)](https://lists.openid.net/pipermail/openid-specs-fapi/2024-February/003062.html) や 3 月以降の EU Payment Wallet スレッド群に連続する論点系列の起点として記録される。

### OpenID Foundation Comments on CFPB Rule 1033 — 2024-01-03 公示

[OpenID Foundation Comments on CFPB Rule 1033 Regarding Open Banking](https://openid.net/oidf-comments-cfpb-rule-1033-regarding-open-banking/) が **2024-01-03 に OIDF 公式から公示**。**前年 2023-12-29 に Nat Sakimura が OIDF を代表して CFPB へ提出したコメントレター**を解説するブログ記事である。論点は以下のとおり。

- 米国 Personal Financial Data Rights Rule（Rule 1033）に「Standardized Communication Protocol」を要求として組み込むべきとの主張
- 「Standardized Communication Protocol」の例として **「FAPI profile of OpenID Connect」と「FAPI 2.0 Security Profile」** を明示
- FAPI が UK Open Banking / Brazil Open Finance / CDR Australia / Saudi Arabia Open Banking で既に採用されている事例を提示
- **「FAPI 2.0 は正式 security analysis を完了し、Final membership voting を経た段階」** と現状を報告
- Open Source Conformance Testing Tools が全 FAPI 版で利用可能と説明

Sakimura が共同議長として OIDF を代表しつつ、米国 Open Banking 規制という最重要市場における「FAPI = 通信プロトコル標準の参照実装」言説を 1 月初頭に世に投じたタイミングが本月の最大の対外発信である。この発信は後の 5 月の本格的 [Letter to the CFPB on US open banking](https://openid.net/letter-cfpb-open-banking/)（Gail Hodges 名義、2024-05-17）に発展する。
