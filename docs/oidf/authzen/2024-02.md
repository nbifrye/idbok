# OpenID Foundation AuthZEN WG 活動レポート (2024年2月)

> 執筆日: 2026-05-22（2024 年 2 月の活動を遡及してまとめたレポートです）

## 1. 概要

AuthZEN Working Group（WG）は、Policy Enforcement Point (PEP) と Policy Decision Point (PDP) の間の認可クエリを標準化することを目的とした OpenID Foundation の WG である。2023 年 10 月に OIDF Board により chartered され、ML アーカイブ（[`openid-specs-authzen`](https://lists.openid.net/pipermail/openid-specs-authzen/)）も同月に開始されており、2024 年 2 月時点では発足からまだ 4 ヶ月目の **「初期仕様策定期」** にある。WG 議長は David Brossard（Axiomatics）と Omri Gazitt（Aserto）が中心となって運営しており、Gerry Gebel（Strata Identity）も招集役・議題告知役として WG オペレーションの中核を担っていた（[ML #95](https://lists.openid.net/pipermail/openid-specs-authzen/2024-February/000095.html) で「all four co-chairs unavailable」との表現があり、当時の co-chair 体制は 4 名構成であった）。

2024 年 2 月の AuthZEN WG は、**「prior art サーベイ期間から、Identiverse 2024（5-28〜31）を初の公開 interop イベントとして照準に定めた具体的な仕様策定期へと移行する転換点」** に位置付けられる。1 月から続いていた Cedar / ALFA / OAuth / OpenFGA など既存認可技術のレビューが 2 月中旬に一段落し、2-13 にエディタ David Brossard が **AuthZEN リポジトリへの 2024 年初の人間コミット**（[commit `878edd6`](https://github.com/openid/authzen/commit/878edd6) ほか 2 件）として Authorization API 仕様ドラフトの大幅な再構成を投入した。これは「**トランスポートをモデルから切り離し、Cedar と ALFA のモデルに基づくより汎用的な情報モデルを提供する**」という方向性を初めて仕様文書本体に反映したコミットであり、後の Authorization API 1.0 ドラフトの章構成（Subjects / Resources / Actions / Context の情報モデル、Access Evaluations API、Resource Search API、Subject Search API、Transport）の **基本骨格がこの月に確立された**。

`openid-specs-authzen` ML への 2 月分投稿数は **21 件**（[2024 年 2 月アーカイブ](https://lists.openid.net/pipermail/openid-specs-authzen/2024-February/thread.html) の `000078`〜`000098`）。スレッド構成は 8 本で、(a) AuthenticateCon CFP への対応（3 通）、(b) 1 月分・2-06 分の議事録共有（4 通）、(c) OpenFGA 招待状（3 通）、(d) 2-20 コール中止通知と payload 文書レビューの誘導（3 通）、(e) Rifaat Shekh-Yusef による payload 文書レビュー（1 通、月末投下）、(f) その他（Regrets、Notes from today's call、Link to today's upcoming meeting notes）で構成される。月内に **3 回の WG コール**（2-06、2-13、2-27）が実際に開催され、HackMD `@oidf-wg-authzen` 上に議事録が公開されている（2-20 は co-chair 全員欠席により中止）。`openid/authzen` リポジトリの 2 月 PR/Issue は **0 件**だが、2-13 の 3 件のエディタ commit により仕様ドラフト本体は大きく書き換わった。

2 月の論点を整理すると、次の 4 点に集約できる:

- **Authorization API ドラフトの再構成着手** — エディタ David Brossard が 2-13 のコール内および前後で `api/authorization-api-1_0.md` を大幅改訂（[commit `878edd6`](https://github.com/openid/authzen/commit/878edd6) +126/-55 行、[`8e678b6`](https://github.com/openid/authzen/commit/8e678b6) +65/-76 行、[`778e7f8`](https://github.com/openid/authzen/commit/778e7f8) +6/-2 行）。Cedar と ALFA を参考にした情報モデル（Subjects / Resources / Actions / Context）を導入し、「The Request」「The Response」章を「The Access Evaluation API Request」「The Access Evaluation API Response」へ改名、判定語彙を「allow/deny」から「Permit」へ変更。これが 2-13 時点で AuthZEN リポジトリへの 2024 年初の人間コミットであり、約 3 ヶ月の prior art サーベイ期間の終結を示す
- **interop scenario としての Todo アプリケーションの確定と payload 文書の起草** — 2-06 コールで Omri Gazitt が **「Stock React app with different backend languages」** をベースに Rick & Morty テーマの Todo アプリを紹介。Morty は自分のタスク編集のみ、Rick は全機能、Jerry は制限的アクセスという role-based ポリシーを実装。2-13 コールで Identiverse interop の正式 scenario として承認され、Omri が interop payload 文書を起草。月末 2-28 に Rifaat Shekh-Yusef が **「Review of 'Payloads for the Todo application interop scenario'」**（[ML #98](https://lists.openid.net/pipermail/openid-specs-authzen/2024-February/000098.html)）で詳細レビューを投げ、これが 3-05 コール議題と 3 月の主要技術スレッドへ直結する
- **OpenFGA を prior art ラインナップへ追加** — 2-16（金）に Andres Aguiar（Auth0/Okta、OpenFGA メンテナ）が AuthZEN WG の prior art series の一環として OpenFGA 単独 presentation を実施（[ML #91](https://lists.openid.net/pipermail/openid-specs-authzen/2024-February/000091.html), [#93](https://lists.openid.net/pipermail/openid-specs-authzen/2024-February/000093.html)）。Cedar / ALFA / OAuth / XACML に続く 5 つ目の prior art として OpenFGA（Zanzibar 系の Relationship-Based Access Control）が WG の評価対象に正式に加わった。2-06 議事録時点では「OpenFGA の技術プレゼンテーション」が議題の 1 項目として既に予告されており、2-16 開催で実施された
- **複数カンファレンスでの発表受理と Identiverse interop 確定** — 2-13 コール議事録の「Conference Updates」節で、David Brossard の Nordic APIs での AuthZEN 発表、Omri Gazitt の EIC パネル受理、Atul Tulshibagwale の Identiverse 登壇、Identiverse interop イベントの開催確定が共有された。2-01〜02-01 の [ML #78〜#80](https://lists.openid.net/pipermail/openid-specs-authzen/2024-February/000078.html) スレッドでは AuthenticateCon CFP の提出方針（Gerry との RSA 共同投稿、または Omri 提出に沿った EIC/Identiverse 風パネル）も合意。WG は 2 月を境に **「内部議論期間から外部露出期間への移行」** を本格化させた

## 2. 公開された仕様・ドラフト改訂

### Authorization API ドラフト（2 月時点の状態）

- **形態**: openid.net/specs/ 配下への正式 publish は **未実施**。`api/authorization-api-1_0.md`（リポジトリ内 markdown）のみが仕様文書として存在。Implementer's Draft 00 publish（後の 2024-08-14）には 6 ヶ月先行する初期段階
- **2 月内のドラフト改訂**: 2024 年に入って初の人間コミット 3 件が 2-13 にエディタ David Brossard から投入され、仕様ドラフトが大きく書き換わった
  - [`878edd6`](https://github.com/openid/authzen/commit/878edd6) **「Started updating the spec based on comments in the mailing list and weekly meetings」**（+126/-55 行）: 「**I started reworking the spec to decouple transport from model and to provide the more generic model we agreed on based on Cedar and ALFA's models**」をコミットメッセージに明記。トランスポート層とデータモデルの分離、情報モデル（Subjects / Resources / Actions / Context）の導入、トランスポート章の追加、用語集の文書末尾への移動などが含まれる
  - [`8e678b6`](https://github.com/openid/authzen/commit/8e678b6) **「Continued work on the response」**（+65/-76 行）: 例として用いる Resource を **「user with attribute names」から「book with library record details」へ変更**。action 定義（access, create, read, update, delete）を definition-list から箇条書きへ整形。「The Request」を「The Access Evaluation API Request」に、「The Response」を「The Access Evaluation API Response」に改名。判定語彙を **「allow/deny」から「Permit」へ変更**。Reason Fields and Objects の章構造を整理
  - [`778e7f8`](https://github.com/openid/authzen/commit/778e7f8) **「Minor edits during the weekly call」**（+6/-2 行）: 2-13 コール中に行われた軽微な編集。Access Evaluation API と Search API の説明に **「non-normative examples」** との表現を追加し、Search API の例として「What can happen?」「Who can edit medical records between 8 am and 3 pm?」「What can happen at 3 pm from Glasgow?」の 3 例を追加
- **2-13 時点の章構成**（[2024-02-13 のドラフト](https://github.com/openid/authzen/blob/878edd6/api/authorization-api-1_0.md)）:
  - 情報モデル: Subjects / Resources / Actions / Context
  - API: Access Evaluations API（単一リソース・単一コンテキストでの判定）、Resource Search API（subject がアクセス可能な全 resource の発見）、Subject Search API（与えられた resource にアクセス可能な全 subject の発見）
  - Transport: REST bindings 実装仕様
  - 用語定義: PDP / PEP 等
  - Security and IANA Considerations
- **位置付け**: 2 月は **「prior art サーベイで得た合意を仕様文書本体に初めて反映した月」**。Cedar の PARC モデル（Principal, Action, Resource, Context）に対し、AuthZEN は Subject に統一しつつも Cedar および ALFA の symmetric な情報モデルを参考にしている点が、コミットメッセージから明確に読み取れる。2-13 時点で既に **Resource Search API / Subject Search API** が章として明示的に章立てされている点が注目される。これは 2025 年 6 月の [PR #113](https://github.com/openid/authzen/pull/113) で「Search 系列は 1.0 から除外して profiles 群へ送る」決定に至るまで、長く WG 内で議論される論点の出発点である

### Interop シナリオ（Todo アプリ）— 2 月内に確定

2-06 コール（[HackMD wg-meeting-20240206](https://hackmd.io/@oidf-wg-authzen/wg-meeting-20240206)）で Omri Gazitt が **「Stock React app with different backend languages」** をベースに、Rick & Morty テーマの Todo アプリケーションを WG に提示。これが AuthZEN の interop scenario として 2-13 コールで承認され、Identiverse 2024 へ向けた共通リファレンス実装として位置付けられた。

- **キャラクター設計と policy 構造**:
  - **Morty**: 自分のタスクのみ編集可（個人ユーザーのデフォルト権限）
  - **Rick**: 全機能利用可（admin 相当の高権限ロール）
  - **Jerry**: 制限的アクセスのみ（read-only または部分的権限のロール）
- **アクション命名規約**: `can_read_user`, `can_read_todos`, `can_create_todo`, `can_update_todo`, `can_delete_todo` などの `can_*` プレフィックス記法（後の 3 月議論で Omri Gazitt が「**no reserved verbs**」を示すための意図的設計と明言）
- **2-13 コール（[HackMD wg-meeting-20240213](https://hackmd.io/@oidf-wg-authzen/wg-meeting-20240213)）での補強議論**:
  - **UX policy vs access control policy の概念分離**: 「UX policy MAY choose to use the access control policy as input」とし、検索 API 等の追加サービスとの併用可能性を確認。AuthZEN の判定 API と、UI が判定結果をどう扱うかは別レイヤーであるという認識の合意
  - **Search language の AuthZEN 仕様からの分離**: 検索クエリ言語は AuthZEN PDP 仕様とは別の optional extension とし、時間をかけて進化させる方針
  - **Kong DevRel との連携**: PEP アプリの担当 vendor として Kong に正式接触する方針合意。Tariq Shaikh（Capital One）と Scott Guyer も demo app 提供者として参加検討
  - **Identiverse interop の正式確認**: Identiverse 2024 で AuthZEN として interop イベントを行うことが正式に確定。詳細は今後の整理待ち
- **2-20 コール中止と payload 文書の起草**: 2-20 は 4 名の co-chair 全員が参加不可となり、Gerry Gebel が [ML #95](https://lists.openid.net/pipermail/openid-specs-authzen/2024-February/000095.html) で「**Due to the unavailability of all four co-chairs (!!), we will cancel today's call**」と中止通知。Gerry は同時に「continued focus on basic permit-deny specification for the interop demo」を求めた。中止通知のスレッド内で Omri Gazitt が [ML #96](https://lists.openid.net/pipermail/openid-specs-authzen/2024-February/000096.html) にて **HackMD 上で起草した interop Payloads 文書**へのリンクを共有し、「**I'm happy to do that next week**」と翌週への持ち越しを提案、Gerry が [ML #97](https://lists.openid.net/pipermail/openid-specs-authzen/2024-February/000097.html) で 2-27 アジェンダへの追加を確認
- **2-27 コール（[HackMD wg-meeting-20240227](https://hackmd.io/@oidf-wg-authzen/wg-meeting-20240227)）での payload 文書のレビュー**:
  - Omri が action 属性の表現方式について「**graphQL does not work this way**」との観点から、汎用的なアプローチではなく **文字列ベースのアプローチが有効** と提案
  - **path と method を context に移動**し、resource context が存在するすべての場所に **`type` フィールドを追加**する変更を実施
  - アプリケーションのソースコードを WG 全体に共有することが合意
  - 出席者: Gerry、Omri、Roland Baum、Atul Tulshibagwale（SGNL）、Dani Katzman、Alex Babeanu、Alex Olivier、Jamie Lin、George Fletcher、Wade Ellery、Victor Lu、Joshua Roberts、Adam Rusbridge、Rifaat Shekh-Yusef、Bjorn Hjelm の少なくとも 15 名

## 3. ミーティングと議論

AuthZEN WG は隔週火曜（米国時間）にコールを開催している。2024 年 2 月の暦上の火曜は **2 月 6 日・13 日・20 日・27 日** の 4 枠で、結果として **2-06、2-13、2-27 の 3 回が開催、2-20 のみ中止**となった。HackMD `@oidf-wg-authzen` にすべてのミーティングノートが残っており、ML 上にも議事録共有（David Brossard 起点、2-06 付の [ML #87](https://lists.openid.net/pipermail/openid-specs-authzen/2024-February/000087.html)〜[#90](https://lists.openid.net/pipermail/openid-specs-authzen/2024-February/000090.html)）が連投されている点で、2024 年 3 月以降の月と比べても **公開議事録が充実した月** である。

[HackMD wg-meeting-20240206](https://hackmd.io/@oidf-wg-authzen/wg-meeting-20240206) ([ML #90](https://lists.openid.net/pipermail/openid-specs-authzen/2024-February/000090.html) で 2-06 22:06 UTC に David Brossard が共有)。出席は 16 名以上で、主要参加者には Atul Tulshibagwale（SGNL）、Jeff Broberg、Joshua Roberts（NIST）、Scott Guyer（Capital One）、Darin McAdams（AWS）、Jason Garbis（Numberline Security）など、認可業界の幅広い vendor 代表が並ぶ。

5. **OpenID 白書発行の検討**: 「authorization design patterns」をテーマとした OIDF 公式 white paper の発行検討を開始。Alex Babeanu がコンテンツ作成のボランティアを募集する役割を担う
