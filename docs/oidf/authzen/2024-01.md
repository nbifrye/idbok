# OpenID Foundation AuthZEN WG 活動レポート (2024年1月)

> 執筆日: 2026-05-22（2024 年 1 月の活動を遡及してまとめたレポートです）

## 1. 概要

AuthZEN Working Group（WG）は、Policy Enforcement Point (PEP) と Policy Decision Point (PDP) の間で交わされる認可クエリの形式を標準化することを目的とした OpenID Foundation の WG である。2023 年 10 月 20 日に OIDF Specs Council によって正式に chartered され、2023 年 10 月 24 日に第 1 回ミーティングを開催した（[OpenID Foundation: Announcing the Authorization Exchange (AuthZEN) Working Group](https://openid.net/announcing-authzen-working-group/)）。共同議長には David Brossard（Axiomatics）と Omri Gazitt（Aserto）を中心とした体制が組まれ、Gerry Gebel（Strata Identity）も招集・議題告知役として WG オペレーションの中核を担う。

2024 年 1 月の AuthZEN WG は、**WG 発足からちょうど 3 ヶ月目にあたる「prior art サーベイ期」のピーク**に位置付けられる。前年 11 月までに Authorization API ドラフトの初版骨格が `api/authorization-api-1_0.md` に投入され、12 月は OIDF 全体の冬季ホリデー期間に重なって活動が静かだったため、年明け 1 月は **「既存の認可技術（Cedar / OAuth / XACML / ALFA / Topaz/Aserto / NIST NGAC）を WG として体系的にレビューし、新仕様の情報モデルと API 設計指針を固める集中期間」** となった。1 月 16 日のコールに新規メンバーとして NIST team / Cloudentity / Radiant Logic / Cerbos の 4 組織が加わるなど、参加 vendor の裾野もこの月に大きく広がっている。

[`openid-specs-authzen` ML の 2024 年 1 月アーカイブ](https://lists.openid.net/pipermail/openid-specs-authzen/2024-January/thread.html) には **31 通**（メッセージ番号 `000047`〜`000077`）が投稿された。スレッド構成は、(a) OIDF 理事会選挙の投票開始通知（`000047`、Mike Leszcz）、(b) 1-16 コール案内および AWS Cedar プレゼン関連のやり取り（`000048`〜`000049`、`000053`〜`000056`）、(c) interop scenarios HackMD 文書の更新（`000050`〜`000051`、David Brossard / Eve Maler）、(d) 東京での OIDF ハイブリッドワークショップ用スライド（`000052`、`000055`）、(e) PEP-PDP API 専用セッション招待状群（`000057`〜`000060`）、(f) 1-16 コール議事録共有（`000061`）、(g) 1-25/1-26 開催の Design patterns / Topaz / NIST NGAC オーバービュー招待状（`000062`〜`000065`、`000075`）、(h) 1-23 付の週次アップデート（`000066`）と、それに続く「PEP-PDP API」「This week's updates」「The Search API」スレッドでの設計議論（`000067`〜`000074`、`000076`〜`000077`）に整理できる。

1 月の `openid/authzen` リポジトリには **新規 Issue / PR は 0 件、main ブランチへの新規 commit も 0 件**（[2024-01 起票 issue 検索結果](https://github.com/openid/authzen/issues?q=is%3Aissue+created%3A2024-01-01..2024-01-31)、[2024-01 起票 PR 検索結果](https://github.com/openid/authzen/pulls?q=is%3Apr+created%3A2024-01-01..2024-01-31)）。仕様ドラフト本体への次の人間コミットは翌 2-13（[`878edd6`](https://github.com/openid/authzen/commit/878edd6) ほか 2 件）を待つことになり、1 月は **「コード成果物よりも、議論・議事録・HackMD 上の interop scenarios 文書という形で勢いを蓄積した月」** と表現できる。

月内に確認できた WG コール・特別セッションは以下の通り（HackMD `@oidf-wg-authzen` 上に議事録が公開されている）:

- **1-09（火）定例コール**: Identiverse パネル受理状況確認、Authorization Design Patterns レビュー、PEP-PDP 通信スキームと prior art（AVP / OAuth / XACML）の議論

- **1-19（金）PEP-PDP API 専用セッション**: XACML / ALFA / JSON prior art を David Brossard が presentation
- **1-23（火）定例コール**: Cedar / ALFA / OAuth レビュー総括、interop scope 合意（5 月までは permit/deny のみ）、interop 参加 vendor の整理、SARE/PARC モデル採用、RFC 9493 参照合意
- **1-25（木）11am PT**: Alex Babeanu リードの Design Patterns 特別セッション（OAuth と P\*P の整合検討）

これら 7〜9 枠のミーティング・特別セッションが 1 ヶ月内に詰め込まれており、**AuthZEN WG 史上最も密度の高い「prior art 集中レビュー期」** だったと評価できる。1 月の論点を整理すると次の 4 点に集約される:

- **prior art サーベイの体系化と「PARC モデル」の WG 内合意** — 1-16 コールで AWS Cedar の PARC モデルが「リクエストの送り方とレスポンスの処理を harmonize する」WG の合意目的に最も近い表現として議論され、1-23 コールでは **「SARE/PARC モデル（subject verb object context）を ALFA / Cedar から採用しつつ独自カテゴリで補完する」** 方針が明文化された。これが翌月 2-13 のエディタコミット（[`878edd6`](https://github.com/openid/authzen/commit/878edd6)）における「Subjects / Resources / Actions / Context の情報モデル導入」の直接の根拠となる
- **「最小スコープ仕様」原則の確立** — 1-23 ML スレッド ["The PEP-PDP API"](https://lists.openid.net/pipermail/openid-specs-authzen/2024-January/000067.html) で David Brossard が「transport と message を分離」「初回 iteration は単純な permit/deny のみ、obligations や advice などの追加 statement は含めない」「attribute-based モデルを ALFA/Cedar に揃える」という 3 原則を提示し、Omri Gazitt が [`000072`](https://lists.openid.net/pipermail/openid-specs-authzen/2024-January/000072.html) で「**we can layer other things once we've declared success on the simple cast**」と全面同意。1-23 議事録で「interop 次ステップは 2024 年 5 月までに Yes/No の二項判定のみ」と明示され、**WG の最小スコープ路線が 1 月後半に確立された**
- **interop 参加 vendor の拡大と PEP/PDP/Demo App の三層構成案** — 1-16 で NIST / Cloudentity / Radiant Logic / Cerbos が、1-30 で Zuplo / SGNL / PlainID / Radiant Logic が interop 関心を表明。1-23 議事録では **「AuthZ vendor: Axiomatics、AWS（webapp 側と AuthZ 側のどちらで参加するか検討中）、3Edges、Aserto、Permit.io」「PEP vendor として Kong、Zuplo を勧誘」「アプリ層に Spring app、OPAL、Todo app、または Jeff Lombardo の Cedar demo を利用」** という三層構成案が初めて整理された。Identiverse 2024（5-28〜31）の pre-conference 期間に interop を実施し本会議で結果を発表する計画も同コールで議論された
- **Design Patterns と AS/PDP 概念の対立議論** — 1-23 の David Brossard 週次アップデート（[`000066`](https://lists.openid.net/pipermail/openid-specs-authzen/2024-January/000066.html)）に対し、Alex Babeanu（3Edges）が [`000068`](https://lists.openid.net/pipermail/openid-specs-authzen/2024-January/000068.html) で「**ほとんどの組織は RBAC を使っており PEP-PDP パターンを使っていない**」「AS（Authorization Server）と PDP の橋渡しが WG mission として critical」と指摘。Brossard も [`000070`](https://lists.openid.net/pipermail/openid-specs-authzen/2024-January/000070.html) で「**the spec was too P\*P-biased**」と認め、Cedar や ALFA の API が 3Edges のようなグラフベースアプローチに本当に適しているか再検証する必要を表明。これが 1-25 の Design Patterns 特別セッションと 1-26 ML [`000077`](https://lists.openid.net/pipermail/openid-specs-authzen/2024-January/000077.html) で Alex が Google Slides を共有した design patterns diagram に発展する

## 2. 公開された仕様・ドラフト改訂

### Authorization API ドラフト（1 月時点の状態）

- **形態**: openid.net/specs/ 配下への正式 publish は **未実施**。`api/authorization-api-1_0.md`（リポジトリ内 markdown）のみが仕様文書として存在。Implementer's Draft 00 publish（後の 2024-08-14）には 7 ヶ月先行する初期段階
- **1 月内のドラフト改訂**: **commit 0 件**。[`openid/authzen` のコミット履歴](https://github.com/openid/authzen/commits/main)を確認すると、直近の人間コミットは 2023-11-15 で、次のコミットは 2-13 まで待つことになる。1 月の WG は **「仕様文書本体を書き換えるよりも、prior art と interop scenarios の議論を通じて改訂方針を固めることに時間を費やした月」** と整理できる
- **HackMD 上での interop scenarios 文書整備**: 1-15 ML [`000050`](https://lists.openid.net/pipermail/openid-specs-authzen/2024-January/000050.html) で David Brossard が、Eve Maler が作成した「AuthZEN Interop Scenarios」HackMD 文書に対し以下の更新を実施
  - 参照 XACML interop 文書からユースケースを抽出して独立節「The Use Cases」に整理
  - 「The Use Cases we want to focus on」節を新設、WG の API 設計議論と整合させる
  - Eve Maler が [`000051`](https://lists.openid.net/pipermail/openid-specs-authzen/2024-January/000051.html) で更新内容を承認し、自身も追加コメントを投入
- **設計原則の WG 合意**（1-23 ML [`000067`](https://lists.openid.net/pipermail/openid-specs-authzen/2024-January/000067.html)〜[`000074`](https://lists.openid.net/pipermail/openid-specs-authzen/2024-January/000074.html) スレッド）:
  - **transport と message の分離**: HTTP ステータスコードはサービス可用性のみを示し、認可判定そのものを返す手段とはしない
  - **初回 iteration は permit/deny の二項判定のみ**: obligations、advice、batch などの追加 statement は対象外
  - **attribute-based model**: ALFA または Cedar に揃える
  - **Subject / Action / Resource / Context の 4 オブジェクト構成**: 各オブジェクトは key-value pair の集合として表現
  - **OpenAPI でスキーマ公開を検討**: ただし HTTP バインディングと status code の規定が必要となる点を Omri Gazitt が留意
  - **配列の扱い**: David Brossard は XACML/JSON の歴史（Subject が object と array の両方を許容すると SDK 複雑化を招いた経験）を引いて、「**最初の interop フェーズでは object のみで、AuthZEN 公式仕様化の段階で batch 用途のため array を導入する**」段階的アプローチを提案
- **RFC 9493 (Subject Identifiers for Security Event Tokens) の参照合意**: 1-23 議事録に明記。Subject 識別子の表現方式として、freeform JSON だけでなく RFC 9493 のフォーマットも許容する設計を採用

## 3. ミーティングと議論

AuthZEN WG は隔週ではなく **毎週火曜（米国時間）に定例コール**を開催している。2024 年 1 月の暦上の火曜は **1-02・1-09・1-16・1-23・1-30** の 5 枠で、HackMD `@oidf-wg-authzen` 上に議事録が公開されているのは **1-09・1-16・1-23・1-30 の 4 回**（1-02 は祝日週で開催記録なし）。加えて、1-18（木）、1-19（金）、1-25（木）、1-26（金）に **PEP-PDP API 専用セッションおよび prior art / design patterns / Topaz / NGAC オーバービュー** が単独セッションとして開催された。**月内 8〜9 枠の WG ミーティング** という密度は、AuthZEN WG 史上でも最も濃密な月の一つである。

### 1 月 9 日（火）定例コール — 設計議論の起点

[HackMD wg-meeting-20240109](https://hackmd.io/@oidf-wg-authzen/wg-meeting-20240109)。出席者として Sean O'Dell、Alex Babeanu、Mike Kiser、Roland Baum、Darin McAdams、David Hyland、Elie Azerad、Jamie Lin、Victor Lu、Wade Ellery、George Fletcher、Ash Narkar、Rifaat Shekh-Yusef、Atul Tulshibagwale（SGNL）の 14 名以上が記録されている。

#### 主な議題と決定事項

1. **管理連絡**: OIDF Community Representative 選挙（1-16 12pm PST 締切）と Identiverse パネル投稿状況の確認
2. **Authorization Design Patterns 文書のレビュー**: フィードバック整理と次回への引き継ぎ
3. **PEP-PDP 通信スキームの議論**: 次回（1-16）コールを「design patterns」用に転用し、Darin McAdams（AWS）が **AWS Cedar の prior art プレゼン** を別途実施する方針を確定
4. **OAuth と認可リクエスト拡張**: Rich Authorization Request (RAR)、resource indicators、transaction tokens が認可コンテキストを伝達する候補メカニズムとして議論されたが、「**RAR 単独では包括的な policy 通信には不十分**」との認識が共有された
5. **データモデルと delegation**: マルチパーティ口座シナリオ、consent management、delegated authorization 構造を議論。George Fletcher が「**現代の UX における認証と認可の相互作用**」を強調
6. **分散 PDP の慎重論**: Wade Ellery が「**PDP 層で分散させ始めると synchronization complexity が生じる**」と警告し、中央集約された Policy Information Point の重要性を強調
7. **サブグループ構造**: API spec とデザインパターン開発のためのサブグループを設置することを合意

### 1 月 16 日（火）定例コール — Cedar PARC モデルと新規メンバー受け入れ

[HackMD wg-meeting-20240116](https://hackmd.io/@oidf-wg-authzen/wg-meeting-20240116)。**NIST team / Cloudentity / Radiant Logic / Cerbos の 4 組織が新規メンバーとして歓迎**された節目のコール。Darin McAdams が事前に [ML #56](https://lists.openid.net/pipermail/openid-specs-authzen/2024-January/000056.html) で **AWS Cedar overview 資料** を共有し、本コールで presentation を実施した。

#### 主な議題と決定事項

1. **Cedar モデルの WG レビュー**: 議事録には「**harmonize how to send a request and process a response**」が WG の合意目的であることが明記。Cedar の **PARC モデル（Principal / Action / Resource / Context）** を「現状の API 設計提案には context handling 能力が欠けている」点と対比して検討。「Principal / Action / Resource / Context を equivalent な要素として扱う Cedar の設計」が議論の焦点に
2. **2 つの論点**:
   - **Policy 自体を評価のために送信することの是非**: プロジェクトスコープ外という意見も存在
   - **データのインクルージョン**: 伝統的な PIP 設計に反するが、スケーラビリティ確保のために検討する余地
3. **Interop デモ形式**: **複数 vendor 対応の Postman collection** という形式が候補として議論された
4. **Action Items**:
   - David Brossard: prior art モデルの比較分析を作成
   - Alex Babeanu: design patterns フォローアップを別途スケジュール
   - チーム: interop scenarios 文書をレビュー
5. **後続セッション予告**: Thursday 11am PT に David Hyland の OAuth 深掘り、Friday に David Brossard の ALFA/XACML 深掘り
6. **Identiverse 言及**: interop exercises を Identiverse で実施する方針再確認

### 4.1 [The PEP-PDP API](https://lists.openid.net/pipermail/openid-specs-authzen/2024-January/000067.html) — 2024-01-23 開始（David Brossard 起点、7 通）

WG として **API 設計原則を最初に明文化したスレッド**。1-23 から 1-24 にかけて活発な議論が展開された。

- **[`000067`](https://lists.openid.net/pipermail/openid-specs-authzen/2024-January/000067.html)（David Brossard、1-23 05:25 UTC）**: 5 つの設計原則を提示
  - **§1.2.1**: transport と message を分離し、HTTP ステータスコードは認可判定ではなくサービス可用性のみを伝える
  - **§2**: 初回 iteration は単純な permit/deny の二項判定のみ、obligations / advice / batch などの追加 statement は対象外
  - **§3**: attribute-based モデルを採用し、ALFA または Cedar と整合させる
  - **§4**: リクエストは Subject / Action / Resource / Context の 4 オブジェクトで構成し、各オブジェクトは key-value pair を含む
  - **§5.2**: レスポンスは認可判定 + 任意で適用された policy 識別子
  - スキーマ公開手段として OpenAPI を検討
- **[`000069`](https://lists.openid.net/pipermail/openid-specs-authzen/2024-January/000069.html)（Scott Guyer、Capital One、1-23 18:55 UTC）**: 項目別フィードバック
  - **§1.2.1 賛成**: Envoy proxy の ext-authz filter と一致する
  - **§2 賛成**: ただし「**search 機能を runtime cluster に持たせるべきではない**」と懸念。PAP に持たせるか、patterns 議論で扱うべきと提案
  - **§5.2**: 自分のユースケースには合う
  - **§3 / §4**: implications を理解しきれていないので説明を要望
- **[`000071`](https://lists.openid.net/pipermail/openid-specs-authzen/2024-January/000071.html)（David Brossard、1-23 19:01 UTC）**: 議論を HackMD へ移行する提案
- **[`000072`](https://lists.openid.net/pipermail/openid-specs-authzen/2024-January/000072.html)（Omri Gazitt、1-23 19:18 UTC）**: 全面同意
  - 「**We can layer other things once we've declared success on the simple cast**」と最小スコープ路線を承認
  - attribute-based model を **non-attribute システムを排除しないように一般化** する必要を指摘。最小要件として「**subject / object / action は type と ID を最低限持つ**」べき
  - **ALFA vs. Cedar の用語論争を避けよ**: 用語の選択そのものではなく一貫性が重要
  - OpenAPI 採用に賛成、ただし HTTP バインディングと status code の規定が必要
  - **配列を最初の case から排除する提案を保持する**べきか問題提起
- **[`000073`](https://lists.openid.net/pipermail/openid-specs-authzen/2024-January/000073.html)（David Brossard、1-24 19:24 UTC）**: 3 論点に応答
  - transport vs. message: HTTP バインディングは必要だが「**message format/schema を transport から cleanly separate**」して実装が好みのトランスポートを選べるように
  - リクエスト形式: 「**SARE / PARC ベースで loosely structured な key-value pair**」を使うことで、Zanzibar 系識別子も非 ABAC モデルも排除しない
  - 配列: XACML/JSON で Subject フィールドが object と array の両方を許容したことが SDK 複雑化を招いた歴史を引き、「**最初の interop フェーズは object のみで、AuthZEN 公式仕様化の段階で batch 用途のため array を導入する段階的アプローチ**」を提案

このスレッドが WG として後の AuthZEN Authorization API 1.0 ドラフトの「Subject / Action / Resource / Context」「Permit/Deny の二項判定」「OpenAPI スキーマ」「ALFA/Cedar との整合」という骨格を文字通り合意形成した瞬間である。

- **interop vendor との接触開始**: David Brossard が Zuplo の Josh に、Omri Gazitt が Kong に接触する action items
- **Identiverse 2024（5-28〜31）への 4 ヶ月カウントダウン**: 1 月末時点で残り 17 週。interop scenarios（HackMD 文書）と message format（4 オブジェクト構造）の確定、PEP/PDP/Demo App 三層構成の vendor 確定、Postman collection ベースの interop デモ準備が並行課題
