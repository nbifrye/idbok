# OpenID Foundation Shared Signals WG 活動レポート (2024 年 3 月)

> 執筆日: 2026-05-22（2024 年 3 月分の遡及レポート。Gartner IAM Summit London で実施された WG 初の対外的な CAEP / SSF / RISC Interop Event が月初に開催され、その成果と次の v1 Final 化に向けた論点整理が WG コール・GitHub に流れ込んだ月）

## 1. 概要

Shared Signals Working Group（以下 SSF WG、旧称 RISC WG）は、ゼロトラスト・継続的アクセス評価のための非同期セキュリティイベント共有プロトコル（SSF / CAEP / RISC）を策定する OpenID Foundation のワーキンググループである。月内の定例 WG コールは Atul Tulshibagwale (SGNL) が司会を担う隔週運用が継続しており、3 月時点では Shayne Miel (Cisco / FragLegs)・Sean O'Dell (Disney)・Apoorva Deshpande (Okta)・Tim Cappalli (Okta)・Jen Schreiber (Workday)・Stan Bounev (VeriClouds)・Dean Saxe (AWS)・Steve Venema (ForgeRock) らが主要参加者として議論に常駐していた。主要成果物は [openid/sharedsignals](https://github.com/openid/sharedsignals) リポジトリで管理されている 3 仕様 (SSF / CAEP / CAEP Interoperability Profile)。

2024 年 3 月は **「Gartner IAM London で実施された初の対外的な Interop Event の余韻を受けて、v1 Final 化に向けた論点整理 (Receiver 公開鍵、StreamConfiguration 必須/任意、Verify response code、SSF vs CAEP の切り分け) が WG コールに集中した月」** にあたる。活動は以下の 4 軸で整理できる:

- **Gartner IAM Summit London (3/3-5) での CAEP / SSF / RISC Interop Event**: 3/3 を会場準備・最終 interop テスト日、3/4-5 を本番展示日として、SGNL CTO の Atul Tulshibagwale がコーディネートする「first-ever CAEP Interoperability Event」が開催された。Gartner アナリスト Erik Wahlstrom が 3/4 に breakout session を主催し、Atul が WG co-chair として interop 結果と参加実装を紹介。SGNL の CAEP Hub は Okta・Cisco・SailPoint・Helisoft 等の Transmitter / Receiver と相互に CAEP signal を授受できることが demo された。月初の 3/5 WG コールでは「ベンダー間で『SSF = CAEP』と認知されてしまう」というメッセージング上の課題が浮き彫りとなった
- **「SSF と CAEP/RISC の切り分け」議論の本格化 (Issue #140 系)**: 3/5 コールで **「人々は shared signals と聞くと CAEP を連想する。これは仕様内で CAEP を例示の中心に据え続けてきた帰結である」**（議事録 2024-03-05 より）との認識が共有され、SSF を CAEP/RISC から独立した汎用フレームワークとして再ポジショニングする必要性が議題化。Disney（privacy event）、FAPI（fraud signal）、SSO 系（onboarding 情報）、passkey 管理（第三者プロバイダ移行時のシグナル交換）等、CAEP 以外のユースケースを起点に SSF の汎用性を可視化する方向で合意された
- **Receiver 公開鍵 / SET 暗号化議論 (Issue #140) と verify event 応答コード議論 (PR #142) の継続**: 2/9 起票の Issue #140（Allow Receiver to supply public key）への +1 賛同が 2/26 に ML に流れたうえで、3/19 コールで OIDC Dynamic Client Registration を流用した公開鍵事前登録案・鍵ローテーション時の複数鍵保持要件・暗号化を stream 単位とするか entity 単位とするかの論点が掘り下げられた。同コールで Apoorva が 2/27 起票の PR #142（verify event 応答コード明確化）を interop テスト時の課題として再提起し、Shayne (FragLegs) が **「これは push-based stream にのみ意味があり、poll-based stream には response code は存在しない。RFC 8935 で push 仕様は既に 202 を必須化している」** とレビューコメントを残した
- **Tim Würtele (SECtim) による editorial PR 2 件のマージ**: SECtim が SSF 仕様本文をレビューし、3/14 に PR #145 (Fix Indefinite Articles Before "SSF") と PR #146 (Minor editorial nits) を起票。両者とも FragLegs と Tim Cappalli のレビュー承認を経て 3/20 に tulshi (Atul) によりマージされた。本月の `main` ブランチへの実質的なコミットはこの 2 件のみ

`openid-specs-risc` ML の本月の人手投稿は **ゼロ**（GitHub bot 通知のみ 10 件前後）。技術討議の中心は WG コール議事録（HackMD）と GitHub PR/Issue 上に集中していた。ML への定期的な議事録共有（4 月以降 Atul が始める運用）はまだ確立しておらず、3/5 / 3/19 のコール議事録は HackMD のみで公開されている。Issue #143 (SSE 提案) のように外部からの提案が来た場合に限り、コメント通知 bot 経由で ML に話題が流れる構造であった。

定例 WG コールは隔週運用下で **3/5 と 3/19 の 2 回開催**。

## 3. ミーティングと議論

3 月の WG 定例コールは隔週運用下で 2 回開催 (**3/5、3/19**)。議事録はすべて [github.com/openid/sharedsignals/wiki/Meetings](https://github.com/openid/sharedsignals/wiki/Meetings) からリンクされた HackMD ページに公開されている。

### 3.1 2024-03-05 定例 WG コール

参加者: Sean O'Dell (Disney)、Dean H Saxe (Amazon)、Steve Venema (ForgeRock)、Jen Schreiber、Stan Bounev (VeriClouds)、Apoorva Deshpande (Okta)（議事録 [HackMD 2024-03-05](https://hackmd.io/@oidf-wg-sse/wg-meeting-20240305) より）。Gartner IAM London 直後の月初コール。Atul は不在で議事録上で司会は明示されていないが、Sean O'Dell と Apoorva が主たる発言者として記録されている。

主要議論:

- **SSF を CAEP/RISC から分離するメッセージング課題 (Issue #140 の周辺)**: WG メンバーが直面している認知バイアスとして、**「人々は shared signals と聞くと CAEP を連想する」**（議事録 2024-03-05 より）という共通認識が確認された。これは本仕様のドキュメント内で CAEP を継続的に例示の中心に据え続けてきた帰結であると整理。SSF が独立した汎用フレームワークであることを示すために、CAEP 以外のユースケースを前面に出す方針で合意した。具体的に提示されたユースケースは:
  - **Disney**: privacy event（プライバシー関連のシグナル交換）
  - **FAPI**: fraud signal（identity signal ではなく不正取引検知系のシグナル）
  - **SSO 系**: onboarding 情報の伝搬
  - **passkey 管理**: 第三者プロバイダ間の passkey 移行時のシグナル交換（業界固有のユースケースとして特に有望と評価）

  仕様本文の non-normative セクションで SSF と CAEP の区別を明確化する方向の改善提案が挙がった

- **新規 event type の standardization 要否議論**: あるメンバーが **「新しい event type を作る場合、GitHub に単独で公開するだけではダメか?」**（議事録 2024-03-05 より）と提起。WG として informal な公開ではなくレビュープロセスと将来的な IANA registry 利用を経た standardization を優先する方針で合意。**標準化と柔軟性のバランス** が論点として明文化された。これは後の 4/25 起票 Issue #158 (Tim Cappalli, Explore machine reachable approach to event definitions) で再燃する「event 定義をどう機動的に増やすか」問題の原型的議論である

- **Prescriptive vs Informative イベントの位置付け**: イベントは「receiver に対して具体的なアクションを mandate するもの」か「単に状態変化を informative に通知するもの」かを巡る論点。Partner からは prescriptive な event type を求める声があると共有され、**死亡通知やデータ legacy planning** のような sensitive シナリオ用に prescriptive event の専用セットを作る案が提示された

- **Use Cases ドキュメントの整理方針**: 後の 4/2 コールで Sean O'Dell が「Thursday/Friday までに markdown ドキュメントを作成する」と引き受けることになる use cases ドキュメント別仕様化の素地が、本コールで提起された CAEP 以外のユースケース列挙の議論として既に芽生えていた

- **次月の開催情報**:
  - 4 月 15 日の週: IIW (Internet Identity Workshop, Mountain View)
  - 同週: OIDF meeting at Google Campus

### 4.1 [openid/sharedsignals: New Issue opened (Issue #143 起票通知)](https://lists.openid.net/pipermail/openid-specs-risc/Week-of-Mon-20240304/001464.html) - github bot, 2024-03-06

linussec による Issue #143「Push based- Incorporate Server-Sent Events (SSE)」起票の bot 通知。本文の要旨:

- 現状の PUSH 実装 (RFC 8935) は Receiver に publicly exposed endpoint を持つことを要求する
- これは運用上の複雑性と scalability 課題を生んでいる
- **SSE** を採用すれば long-held HTTP connection 経由でリアルタイム通信を実現でき、public endpoint 要件を排除できる
- 利点: 運用簡素化、HTTP リクエスト数削減、attack surface の縮小、ポーリング不要のリアルタイム通知、既存 web 標準による実装容易性

この提案は ML での個別レスポンスは生まなかったが、GitHub Issue 本体に複数の technical コメントが連投され、議論の中心がそちらに移った。

### 4.2 [openid/sharedsignals: Comment created on issue 143 (SSE は server-to-server ではない、との反論)](https://lists.openid.net/pipermail/openid-specs-risc/Week-of-Mon-20240304/001465.html) - github bot, 2024-03-06

Issue #143 への最初の反論コメントの bot 通知。要旨は **「Server Sent Events is a web technology for client to server communication. SSF is not designed for client to server use」** という指摘で、SSE は本質的に server-to-client メッセージング技術であり、Shared Signals Framework が想定する双方向協調モデルにそぐわないとする立場。続く 001466（同日、別コメンタ）では「議論しているのはまさに server-to-client（Transmitter → Receiver）通信であり、Go / Python / Node.js 等のバックエンドにも SSE 実装は存在する。SSE は HTTP endpoint を持てない Receiver にとって reasonable な代替になる」と反論があり、001467（3/7、第三者コメンタ）では **「WebSockets を含む他の双方向通信方式にも対応できるよう、SSE / WebSocket 等を扱える extension point を設けるべき」** と提案が広がった。

### 4.3 [openid/sharedsignals: Comment created on issue 143 (SSF Slack での議論結果)](https://lists.openid.net/pipermail/openid-specs-risc/Week-of-Mon-20240318/001470.html) - github bot, 2024-03-19

3/19 WG コール開催日に投稿された Issue #143 への WG 公式見解コメントの bot 通知。SSF Slack channel での議論を踏まえた結論として、要旨:

- **「SSF was explicitly designed to be server-to-server」** （SSF は明示的に server-to-server を前提に設計された）
- frontend SPA / device agent / firewall のように push endpoint を持てない実体へ拡張する議論自体は理論的に可能だが、**v1 リリース後まで postpone する** ことを WG として優先
- 暫定的な代替手段として:
  1. polling（特に long-polling）の利用
  2. **non-SSF 通信**: 標準的なサーバを SSF の Receiver として立て、その下流から SPA 等へ SSE で配信する 2 段構成

このコメントが事実上 Issue #143 を v1 Final 後送りの open issue として確定させた。

### 4.4 [openid/sharedsignals: New Issue opened (Issue #144 起票通知)](https://lists.openid.net/pipermail/openid-specs-risc/Week-of-Mon-20240311/001468.html) - github bot, 2024-03-14

authlete の TakahikoKawasaki による Issue #144「SSF: Example of Stream Creation Response」起票の bot 通知。要旨は **「Section 7.1.1.1 の正規仕様文では Stream Creation 成功時の応答コードは `201 Created` と定められているが、その直後の non-normative example が `HTTP/1.1 200 OK` になっている。Example を `HTTP/1.1 201 Created` に修正すべき」** という低リスクだが重要な spec-vs-example の整合性バグ報告。続く 001469（3/16 起票通知）の Issue #147 (Update Stream Status Response の `"status": "paused",` trailing comma 問題) と合わせ、川崎氏のレビューが SSF spec の implementer から見たエラーパスを 2 件 spot し、v1 Final 化前の cleanup 対象として `vID-03` ラベル付きで管理されることになった。

### 5.1 [openid/sharedsignals#143](https://github.com/openid/sharedsignals/issues/143) — Push based- Incorporate Server-Sent Events (SSE)

- author: linussec
- 起票: 2024-03-06 / 状態: open のまま
- ラベル: `enhancement`, `spec:SSF`

外部コミュニティから WG に流れ込んだ最初の本格的な技術提案。本文の要旨:

- RFC 8935 ベースの PUSH delivery は Receiver に publicly exposed endpoint を要求する
- これは特に企業ネットワーク内 Receiver や frontend agent にとって運用負担が大きい
- **SSE による long-held HTTP connection** を delivery method の一つとして追加することで、public endpoint なしで real-time push 受信が可能になる
- 派生利点: HTTP 数削減、attack surface 縮小、既存 web 標準による実装容易性

GitHub Issue 上では起票当日から 4 つのスレッドが分岐して議論された:

- 反対派の主張: **「SSE is a web technology for client to server communication. SSF is not designed for client to server use」** — SSE は本質的に server → client 一方向であり、SSF の Transmitter → Receiver モデルとは抽象レベルが違う
- 中立派の主張: **「SSF の Transmitter → Receiver もまさに server-to-client（Transmitter から見れば下流は client）であり、Go / Python / Node.js にも SSE backend 実装はある。HTTP endpoint を持てない Receiver にとって reasonable」**
- 拡張派の主張: **「SSE だけでなく WebSocket を含む双方向通信方式も使えるよう、delivery method を pluggable な extension point とすべき」**
- 最終的な WG 見解 (3/19 投稿、SSF Slack での議論を踏まえた集約): **「SSF was explicitly designed to be server-to-server. SSE 等への拡張は理論的に可能だが v1 リリース後に検討する。暫定回避策は (1) long polling か (2) 標準サーバを SSF Receiver とし下流に SSE する 2 段構成」**

この issue は本月時点でも open のまま残り、SSF v1 Final 化の post-v1 検討事項として継承される。

### 5.2 [openid/sharedsignals#140](https://github.com/openid/sharedsignals/issues/140) — Allow Receiver to supply public key（3 月活動分）

- author: FragLegs (Shayne Miel, Cisco)
- 起票: 2024-02-09 / 状態: open（本月時点）
- ラベル: `spec:SSF`, `vFuture`

2 月起票だが、2/26 に ML 経由で **「+1 to enabling optional encryption」** の賛同コメントが入り、3/19 コールで本格的に深掘りされたため本月の主要 item として取り上げる。本文の要旨:

- 現状 SSF は **Transmitter 側のみが well-known と `jwks.json` endpoint で公開鍵を公開** している
- SET には PII が含まれる可能性があり、署名だけでなく **暗号化** したいベンダー需要がある
- 暗号化のためには **Receiver 側にも公開鍵を持たせる** 必要があるが、現状 spec はこれをカバーしていない
- Receiver の機能を Transmitter と同等水準まで引き上げる効果も持つ

3/19 コールでの深掘りで以下が論点として可視化された:

- OIDC Dynamic Client Registration による公開鍵 / audience の事前登録
- 鍵ローテーション時の Transmitter 側複数鍵保持
- 暗号化の粒度（stream 単位か entity 単位か）— stream 横断で一貫した security property を維持する方が望ましいとの方向性

この議論を Shayne が引き取って 4/2 起票の PR #148 (Optional receiver_key to enable encryption of SETs) に結実させ、最終的に 4/2 コールで **「暗号化は advanced use case、v1 Final 後に対応」** という整理に至る経緯の出発点となった。

### 5.3 [openid/sharedsignals#145](https://github.com/openid/sharedsignals/pull/145) と [#146](https://github.com/openid/sharedsignals/pull/146) — Editorial PR 2 件

- author: SECtim (Tim Würtele)
- 起票: 2024-03-14 / マージ: 2024-03-20

外部コントリビューターである Tim Würtele (SECtim) が SSF spec 本文をレビューし、editorial 修正を 2 件並行起票:

- **PR #145**: SSF 略号前の不定冠詞修正。"a SSF Event" / "a SSF receiver" → "an SSF Event" / "an SSF receiver"。SECtim は **「The spec contains multiple instances of phrases like 'a SSF Event', 'a SSF receiver', etc. These should be 'an SSF...'」** と Merriam-Webster と APA Style の article-before-acronym ルールを引用して説明
- **PR #146**: より雑多な editorial 修正。特に Discovery section への参照が **「is specified in the Discovery Section 6 section.」** と冗長になっていた箇所を、spec 内の他の参照と整合する **「is specified in the Discovery section (Section 6).」** に修正。その他複数の typo 修正と、レビューで FragLegs が提案した文法修正の取り込み

両者とも FragLegs (Shayne)、timcappalli (Tim Cappalli) のレビューを経て tulshi (Atul) によりマージされた。PR #146 では FragLegs が **「one tiny nit on your nit」** と冗談混じりに自身の nit fix への nit を返すやり取りが記録されている。これらの merge commit が ML に流れた 001471 / 001472 が、本月の ML への bot 通知の中で最も「成果報告」に近い性質を持つ投稿となった。

### 5.4 [openid/sharedsignals#142](https://github.com/openid/sharedsignals/pull/142) — Clarify verify event response code（3 月活動分）

- author: appsdesh (Apoorva Deshpande)
- 起票: 2024-02-27 / 最終的に 2024-04-16 に Abandoned で close

2 月末起票で本月 3/19 に重要レビューが入った PR。本文の要旨は **「Transmitter が verify event を receiver に送った際の response code に関するガイダンスを明確化する」** というもの。

3/19 コールで Apoorva が「interop テストで実装間ばらつきがある」と再提起したのを受けて、3/19 中に FragLegs (Shayne) が GitHub 上でレビュー changes を要求:

> This would only make sense if the Receiver had a push-based stream set up. There is no response code for poll-based streams.

さらに FragLegs は RFC 8935 を参照して **「push spec で既に 202 Accepted は verify event が正しく形成されている場合に必須化されている」** と指摘。本コール時点ではこれを踏まえて push spec への reference を本 PR に追加する方針となったが、最終的には 4/2 コールでの暗号化議論と同様「v1 Final 化優先」方針に従って、4/16 に appsdesh が **「Abandoning this」** と取り下げる結末で 4 月以降に決着する。
