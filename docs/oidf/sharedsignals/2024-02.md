# OpenID Foundation Shared Signals WG 活動レポート (2024 年 2 月)

> 執筆日: 2026-05-22（2024 年 2 月分の遡及レポート。3/3-5 Gartner IAM Summit London で開催される初の対外 CAEP Interop Event の直前期にあたり、online interop テスト (2/3-3/2) が走るなか、新規 CAEP イベント (`Session Established` / `Session Presented`) の提案、Receiver 公開鍵による SET 暗号化議論 (Issue #140) の本格化、Stuttgart 大学による Formal Security Analysis の準備が並行進行した月）

## 1. 概要

Shared Signals Working Group（以下 SSF WG、旧称 RISC WG）は、ゼロトラスト・継続的アクセス評価のための非同期セキュリティイベント共有プロトコル（SSF / CAEP / RISC）を策定する OpenID Foundation のワーキンググループである。月内の定例 WG コールは Atul Tulshibagwale (SGNL) が司会を担う隔週運用が継続しており、2 月時点では Shayne Miel (Cisco / FragLegs)・Apoorva Deshpande (Okta / appsdesh)・Aaron Parecki (Okta)・Tim Cappalli (Okta)・Sean O'Dell (Disney)・Mike Kiser (SailPoint)・George Fletcher (Capital One)・Stan Bounev (VeriClouds)・Tom Sato (VeriClouds)・Nancy Cam-Winget (Cisco)・Phil Windley (AWS)・Dean Saxe (AWS)・Jen Schreiber・Marcus Almgren (University of Stuttgart)・Tim Würtele (SECtim) らが ML / コール / GitHub のいずれかに名前を出している。主要成果物は [openid/sharedsignals](https://github.com/openid/sharedsignals) リポジトリで管理されている 3 仕様 (SSF / CAEP / CAEP Interoperability Profile)。

2024 年 2 月は **「3/3-5 Gartner IAM London Interop Event の直前期として online interop テスト (2/3-3/2) が走るなか、新規 CAEP イベント (`Session Established` / `Session Presented`) の提案、Receiver 公開鍵による SET 暗号化議論 (Issue #140) の起票と急速な賛同形成、Stuttgart 大学による Formal Security Analysis の段取り合意が並行進行した月」** にあたる。活動は以下の 5 軸で整理できる:

- **新規 CAEP イベント 2 種の提案 (`User Present` → `Session Presented` への改名)**: 2/6 コール翌日の 2/7 に Atul Tulshibagwale が **「ユーザーセッションの確立とユーザープレゼンスの観測を示す 2 種の新規イベントタイプを SGNL チームで考案した」** として ML にスライドを共有。Dean Saxe (AWS) が **「FIDO の uaf プロトコルが既に user presence の概念を持つ。命名衝突を避けるべき」** と即日指摘し、Atul は 2/8 に **「Session Presented に改名し、スライドを更新した」** と返信。2/20 コールではこの 2 イベントが正式議題として 1 時間扱われ、`session fingerprint` 抽象化・「初回確立 vs 再来訪」の意味区別・コンテキストデータ (IP、プロトコル) の扱い・プライバシ懸念 (Sean O'Dell からの PPID 提案) が議論された
- **Issue #140 (Allow Receiver to supply public key) の起票と賛同形成**: 2/9 に Shayne Miel (FragLegs, Cisco) が **「現状 SSF は Transmitter 側のみが well-known と jwks.json で公開鍵を公開している。SET には PII が含まれることがあり、署名だけでなく暗号化したい需要がある。Receiver を SSF spec の first-class citizen に格上げすべき」** として起票。同日中に Apoorva (Okta)・川崎貴彦 (authlete) が長文の技術コメントを連投し、川崎氏は **「OID4VCI の `credential_response_encryption` のように、JWK 形式の公開鍵と JWE alg/enc を runtime に渡す柔軟な方式」** を提案。2/11 には FragLegs が **「@TakahikoKawasaki その案がよい。StreamConfiguration に Receiver 提供の optional フィールドを追加するのが poll-based Receiver にも負担が少ない」** と合意形成。2/26 には awoie (Oliver Terbu)・Phil Windley・Dean Saxe (AWS) からそれぞれ「+1 to enabling optional encryption」「+1 ... @TakahikoKawasaki の案がよい」「SCIM 内 SETs 作業でも同じ需要が出ている。TLS termination 越し PII 保護のため必要」と 3 連続賛同が入り、WG コンセンサスが ML 上でほぼ固まった
- **Issue #141 (StreamConfiguration の optional / required フィールド明示) の起票**: 同じく 2/9 に FragLegs が **「`description` フィールドだけが optional 明示されており、他のフィールドが required なのか optional なのか曖昧。全フィールドを明示すべき」** と起票。bug ラベルが付与され `vID-03` (Implementer's Draft 3 候補) ターゲットに位置付けられた
- **PR #142 (Clarify verify event response code) の起票**: 2/27 に Apoorva Deshpande (appsdesh) が **「Transmitter が verify event を receiver に送った際の応答コードに関する明確なガイダンスが必要」** として起票。これは 3/3-5 Gartner Interop Event 直前の online テスト (2/3-3/2 期間中) で実装間のばらつきが浮上したことを背景としており、3/19 コールでの FragLegs レビュー (RFC 8935 への push spec 参照を要求) へとつながる
- **Stuttgart 大学による Formal Security Analysis の段取り**: 2/6 コールおよび 2/7 ML 投稿で Marcus Almgren (Stuttgart) が **「OpenID Foundation が委託する形式的セキュリティ解析を 3/1-4/30 (most likely) に Section 6 の configuration / discovery を中心に実施する。WG 内で liaison 1 名を指名してほしい」** と告知。Aaron Parecki が **「FAPI と同じく形式解析の歴史的前例では仕様への大規模変更は不要」** とコメント。FAPI WG の前例を踏襲する形で進行することが合意された

`openid-specs-risc` ML の本月の人手投稿は **6 件**（2/6 Atul Call notes、2/7 Atul Proposing two new CAEP event types、2/7 Marcus Shared Signals Formal Analysis、2/12 Dean Saxe Re: Proposing、2/14 Atul Re: Proposing、2/20 Atul Call notes）。これに加えて GitHub bot 通知 (Issue #140 起票 + コメント 6 件、Issue #141 起票、PR #142 commit) が断続的に流れた。技術討議の中心は WG コール議事録（HackMD）と GitHub Issue / PR 上にあり、ML はそれらへのポインタと議題提起の役割を果たしていた。

定例 WG コールは隔週運用下で **2/6 と 2/20 の 2 回開催**。なお 2/20 コール末尾で Atul は **「次回 3/5 のコールは多くのメンバーが Gartner IAM Summit London (3/3-5) に出席するため、3/19 に振り替える」** と告知している。

## 3. ミーティングと議論

2 月の WG 定例コールは隔週運用下で 2 回開催 (**2/6、2/20**)。議事録はすべて [github.com/openid/sharedsignals/wiki/Meetings](https://github.com/openid/sharedsignals/wiki/Meetings) からリンクされた HackMD ページに公開されている。

### 3.1 2024-02-06 定例 WG コール

参加者: Atul Tulshibagwale (SGNL)、Apoorva Deshpande (Okta)、Shayne Miel (Cisco)、Aaron Parecki (Okta)、Phil Windley、Marcus Almgren (Stuttgart)、Stan Bounev (VeriClouds)、Tim Würtele (SECtim)（議事録 [HackMD 2024-02-06](https://hackmd.io/@oidf-wg-sse/wg-meeting-20240206) より）。Atul が議事録を 2/6 中に ML に共有 (msg 001448)。

主要議論:

- **PR #134 (Interoperability への OAuth 詳細取り込み) の OAuth セキュリティ十分性論争**: Apoorva が **「PR の意図は SSF と OAuth の併用方法を仕様化することだ」** と趣旨説明した上で、Shayne Miel (Cisco) が **「Duo の用途では OAuth は十分なセキュリティを提供しない (HMAC signed user request 等が必要なケースがある)」**（議事録 2024-02-06 より）と懸念を提起。これに対して Aaron Parecki が **「自前の認可スキームを作る方が OAuth より安全とは通常言えない」** と反論。

  Aaron はさらに **「Interop プロファイルに 2 層のセキュリティを設けてはどうか。basic は bearer token、上位は higher security profile」** と段階的セキュリティプロファイル案を提示。Atul は **「Interop プロファイルで choices を与えると interop でなくなる」** とこれを牽制した。

  Shayne は SSF の機能領域である **Stream Management** と **stream control** の 2 つを切り口に、それぞれ別のセキュリティ要件を適用可能とする方向の妥協案を示唆。結論は持ち越し。

- **Formal Security Analysis のスコープと段取り**: Marcus Almgren が **「OpenID Foundation が委託する形式的セキュリティ解析がまもなく開始し、夏まで継続する。Stuttgart 大学が実施し、Section 6 の configuration および discovery メカニズムが対象。FAPI で実施した形式解析と同じモデル」**（議事録 2024-02-06 より）と告知。Aaron Parecki は **「歴史的前例では仕様への変更は最小限で済む」** と楽観的見通しを共有。WG 内 liaison を 1 名指名する必要性が共有された

- **アクションアイテム**: 明示的なアクションアイテムは議事録に記録されていない (議事録末尾の Action Items セクションは記述なしで終了している)

### 3.2 2024-02-20 定例 WG コール

参加者: Mike Kiser (SailPoint)、Atul Tulshibagwale (SGNL)、Tom Sato (VeriClouds)、Shayne Miel (Cisco)、Apoorva Deshpande (Okta)、George Fletcher (Capital One)、Nancy Cam-Winget (Cisco)、Ravi Chhetri (VeriClouds)、Stan Bounev (VeriClouds)、Jen Schreiber、Tim Cappalli (Okta)、Sean O'Dell (Disney)（議事録 [HackMD 2024-02-20](https://hackmd.io/@oidf-wg-sse/wg-meeting-20240220) より）。Atul が議事録を 2/20 中に ML に共有 (msg 001459)。アジェンダは「新規 CAEP イベント」と「SSF を CAEP / RISC から切り離す方向性」の 2 本立て。

主要議論:

- **`session fingerprint` 抽象化の議論**: 提案された新規 CAEP イベントには `session fingerprint` という claim を含める案があったが、Shayne Miel は **「fingerprint はセッションを識別 (identify) するものではなく、セッションの『性質 (qualities)』を表現するもの」**（議事録 2024-02-20 より）と整理。WG として fingerprint を event subject から分離し、変化検出を可能にする独立 claim として扱う方向で合意

- **`Session Established` vs `Session Presented` の意味区別**: Atul は **「session established は『このユーザーを初めて観測した』を意味し、session presented は再来訪を意味する」**（議事録 2024-02-20 より）とふたつのイベントの違いを説明。Shayne は **「実用上、established イベントは少数で済むが、presented イベントは多数発火することになる」** と運用観点でのメリットを指摘。Machine identity の扱いも論点に上った

- **コンテキストデータの含め方**: George Fletcher が **「セッションに関するコンテキストデータ (IP アドレス、プロトコル等) を、その構成方法を prescribe せずに含められるべき」**（議事録 2024-02-20 より）と提案。複数チャネル間での相関 (cross-channel correlation) を支援する観点

- **Interop のための claim 標準化**: Apoorva Deshpande が **「interop のため claim を標準化することが重要。コンテキストデータが fingerprint の計算に影響を与えるべきかどうかは要検討」** と発言。fingerprint 計算アルゴリズムを過度に prescribe せず、意味的解釈を標準化する方向

- **プライバシ懸念と PPID 代替案**: Sean O'Dell (Disney) が **「fingerprinting によるプライバシリスクがある」** と懸念を提起し、**「より強いプライバシ保護を持つ PPID (Pairwise Pseudonymous Identifier) 系の代替を検討すべき」** と提案

- **次回コールの日程変更**: コール末尾で Atul は **「次回 3/5 のコールは多くのメンバーが Gartner IAM summit London (3/3-5) に出席するため、3/19 に振り替える。本日議論が及ばなかった『SSF を CAEP/RISC から切り離す』アジェンダ項目を 3/19 で扱う」**（ML msg 001459、議事録 2024-02-20 より）と告知。新しい HackMD ノートを 3/19 用に作成済みと伝えた

- **アクションアイテム**: 議事録上で明示的にリストアップされたアクションアイテムは記述されていない

### 4.2 [Proposing two new CAEP event types (新規 CAEP イベント提案スレッド)](https://lists.openid.net/pipermail/openid-specs-risc/Week-of-Mon-20240205/001449.html) - Atul Tulshibagwale, 2024-02-07 起点

### 4.3 [Shared Signals Formal Analysis (Stuttgart 大学による形式解析の段取り告知)](https://lists.openid.net/pipermail/openid-specs-risc/Week-of-Mon-20240205/001456.html) - Marcus Almgren, 2024-02-07

### 5.1 [openid/sharedsignals#140](https://github.com/openid/sharedsignals/issues/140) — Allow Receiver to supply public key

- author: FragLegs (Shayne Miel, Cisco)
- 起票: 2024-02-09 14:27 UTC / 状態: open のまま
- ラベル: `spec:SSF`, `vFuture`
- 2 月内コメント数: **6 件**

本月最も活発に議論された Issue。本文の要旨:

- 現状 SSF は **Transmitter 側のみが well-known と `jwks.json` endpoint で公開鍵を公開** している
- これにより Receiver は受信した SET の署名を検証できる
- しかし SET には **PII (personally identifying information) が含まれることがあり**、署名だけでなく **暗号化** したい需要が一部ベンダーにある
- 暗号化のためには **Receiver 側にも公開鍵を持たせる** 必要があるが、現状 spec はこれをカバーしていない
- SSF spec 全体が Transmitter 中心の記述になっており、Receiver を **first-class citizen** に格上げすべき

2 月内のコメント時系列:

- **2024-02-09 17:57 UTC, appsdesh (Apoorva Deshpande, Okta)**: 過去 WG コール (2023-09-05) で同様の問題提起をしたことを参照リンク付きで言及。「Receiver metadata documentation が欠如している件は前から議題になっていた」と整理。**「SET 暗号化は RFC 8417 (SET 仕様本体) に組み込むか、SSF 仕様内で個別対応するかの選択がある」** と論点設定。さらに **「(1) events オブジェクトのみを暗号化し、stream ID を JWT のプライマリ claim としてルーティングに使う方式 (RFC 8417 拡張案)、(2) per-stream の unique key か per-receiver の unique key かという暗号化粒度の選択」** という 2 軸の設計選択を提示

- **2024-02-09 23:35 UTC, TakahikoKawasaki (川崎貴彦, authlete)**: 別アプローチを提案。**「従来は OpenID Connect Dynamic Client Registration のように事前登録か公開鍵公開のどちらかが必要だった。新しい flexible な方法として、OID4VCI の `credential_response_encryption` のように runtime に JWK と JWE alg/enc を渡す方式がある」**。具体的には JSON オブジェクトで (1) JWK 形式の公開鍵 (RFC 7517)、(2) JWE alg (key encryption)、(3) JWE enc (content encryption、RFC 7516) の 3 要素を構成する案

- **2024-02-11 15:05 UTC, FragLegs (Shayne Miel, Cisco、起票者)**: **「@TakahikoKawasaki その案がよい。StreamConfiguration に Receiver が stream 作成・更新時にセットする optional な JSON フィールドを追加する。これは Receiver にとって負担が小さく、特にどの endpoint もホストしない poll-based Receiver にとっても扱いやすい」** と賛同。さらに **「Transmitter 側は SET を JWS でただ署名するのではなく、JWE として全体を暗号化する。PII は `sub_id` claim にもトップレベルで現れることがあるため、events フィールドのみの暗号化では不十分」** と暗号化対象スコープを events から SET 全体に拡張する見解

- **2024-02-26 14:22 UTC, awoie (Oliver Terbu)**: **「+1 to enabling optional encryption」** — 簡潔な賛同

- **2024-02-26 16:34 UTC, windley (Phil Windley)**: **「+1 to optional encryption and I also like. @TakahikoKawasaki's suggestion」** — 川崎案への明示的賛同

- **2024-02-26 19:42 UTC, dhs-aws (Dean H. Saxe, AWS)**: **「これは SCIM 内 SETs を用いる作業でも上がっている課題だ。SET 暗号化メカニズムが必要であることに同意する。特に Receiver の手前で TLS termination が行われるケースで data in transit を保護するため」** — クロスプロトコル (SCIM Events) からの validation コメント

これら 6 コメントによって 2 月末時点で **「SET 暗号化を SSF spec で正式サポートする方向、川崎案 (StreamConfiguration の optional field に JWK + JWE alg/enc を埋め込む) を有力候補とする方向」** での WG コンセンサスがほぼ ML 上で形成された。3/19 コールでこの議論を踏まえて Shayne が「SET 暗号化と Dynamic Client Registration を扱う PR を準備する」と引き受け、4/2 起票の PR #148 (Optional receiver_key to enable encryption of SETs) に結実する。

### 5.2 [openid/sharedsignals#141](https://github.com/openid/sharedsignals/issues/141) — Mark fields optional or required in StreamConfiguration

- author: FragLegs (Shayne Miel, Cisco)
- 起票: 2024-02-09 19:02 UTC / 状態: open（本月時点、後に 2024-05-23 close）
- ラベル: `bug`, `spec:SSF`, `vID-03`
- 2 月内コメント数: **0 件**

本文の要旨:

- StreamConfiguration セクションで **`description` フィールドだけが「An optional string to describe the properties of the stream」と optional 明示** されている
- 他のフィールドには required / optional の明示がない
- これは「他のフィールドはすべて required と解釈すべきなのか、それとも個別に明示すべきなのか」という曖昧性を生む
- 解決策の選択肢: (1) `description` 以外をすべて required と推論する、(2) 各フィールドに required / optional を明示的にドキュメント化する

本月内のコメントはゼロだが、`bug` および `vID-03` (Implementer's Draft 3 候補) ラベルが付与されたことから、SSF v1 Final 化前に必ず解決すべき cleanup 項目として位置付けられた。3/19 コールで Mark (姓不詳) が「他仕様で conditionally required な項目をどう表現しているかを調査するべき」と提案し、調査タスク化される。最終的に 5/23 に close。

### 5.3 [openid/sharedsignals#142](https://github.com/openid/sharedsignals/pull/142) — Clarify verify event response code

- author: appsdesh (Apoorva Deshpande, Okta)
- 起票: 2024-02-27 18:38 UTC / 状態: open（本月時点）
- 2 月内コミット: 1 件 (commit `c54411`、2/27 push)

本文（PR 説明）の要旨は **「Transmitter が verify event を receiver に送った際の response code に関する明確なガイダンスを提供する」**。これは 3/3-5 Gartner Interop Event 直前の online interop テスト期間 (2/3-3/2) で実装間のばらつきが浮上したことを背景とした「interop ブロッカー候補」の整理 PR である。

2 月内のレビューコメントは入らず、3/19 コールで Apoorva が再提起した際に FragLegs (Shayne) が **「これは push-based stream にのみ意味があり、poll-based stream には response code は存在しない。RFC 8935 で push 仕様は既に 202 Accepted を必須化している」** とレビュー changes を要求するに至る。最終的に「v1 Final 化優先」方針に従って 4/16 に Apoorva が **「Abandoning this」** と取り下げて close される。

PR としては成果に至らなかったが、**この PR が浮上させた「verify event の response semantic は push / poll のいずれを前提とするか」という論点自体は重要** で、後の Implementer's Draft 3 における verify event 章の整理に反映されている。
