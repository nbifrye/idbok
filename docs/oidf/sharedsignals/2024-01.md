# OpenID Foundation Shared Signals WG 活動レポート (2024 年 1 月)

> 執筆日: 2026-05-22（2024 年 1 月分の遡及レポート。3/3-5 Gartner IAM Summit London Interop Event の事前準備期にあたり、CAEP Interoperability Profile への OAuth 詳細取り込み (PR #134) のレビューサイクル、PR #137 (verification event の `opaque` 形式必須化) の merge、新たな共同議長 (Shayne Miel / Sean O'Dell) の選出、Tokyo Hybrid Workshop での SSF プレゼンテーションが並行進行した月）

## 1. 概要

Shared Signals Working Group（以下 SSF WG、旧称 RISC WG）は、ゼロトラスト・継続的アクセス評価のための非同期セキュリティイベント共有プロトコル（SSF / CAEP / RISC）を策定する OpenID Foundation のワーキンググループである。月内の定例 WG コールは Atul Tulshibagwale (SGNL) が司会を担う隔週運用が継続しており、1 月時点では Atul Tulshibagwale (SGNL)・Apoorva Deshpande (Okta / appsdesh)・Shayne Miel (Cisco Duo / FragLegs)・Sean O'Dell (Disney)・Tim Cappalli (Okta)・Tom Sato (VeriClouds)・Stan Bounev (VeriClouds)・Mike Kiser (SailPoint)・Peter Travers (MongoDB)・andrei-galkin・Gail Hodges (OIDF Executive Director) らが ML / コール / GitHub のいずれかに名前を出している。主要成果物は [openid/sharedsignals](https://github.com/openid/sharedsignals) リポジトリで管理されている 3 仕様 (SSF / CAEP / CAEP Interoperability Profile)。

2024 年 1 月は **「3/4-5 Gartner IAM Summit London Interop Event の事前準備期として CAEP Interoperability Profile の OAuth 詳細取り込み (PR #134) レビューサイクルが進行し、PR #137 (verification event の `opaque` sub_id 形式必須化) が merge され、新たな共同議長 (Shayne Miel / Sean O'Dell) が選出された月」** にあたる。活動は以下の 4 軸で整理できる:

- **共同議長体制の拡張 (Anabelle 退任、Shayne Miel / Sean O'Dell 就任)**: 1/9 コールで Atul は **「Anabelle が共同議長を退任する。Shayne Miel と Sean O'Dell が共同議長就任に関心を表明した」** と告知し、次回コール (1/23) までに反対意見がなければ就任を正式承認する手順を提案。1/23 までに ML 上で反対意見の表明はなく、Atul Tulshibagwale (SGNL)・Tim Cappalli (Okta)・Shayne Miel (Cisco Duo)・Sean O'Dell (Disney) の 4 名体制が確定した
- **PR #137 (verification event の `opaque` sub_id 必須化) の merge**: 1/8 に FragLegs (Shayne Miel) が起票。**「Verification events MUST include an opaque sub_id. Since Transmitters MUST send verification events, then Receivers MUST be prepared to accept them.」** という主張で、Transmitter が必ず送信する verification event 用に Receiver も `opaque` 形式の受領を必須とする方向の変更。1/9 コールでの議論を受け 1/11 に追加 commit (`ffdf2c`: Verification events に限定する明示文を追加) を投入。tulshi (Atul) と appsdesh (Apoorva) が承認し、1/15 に `7b00ef` で `main` に merge された
- **PR #134 (Interoperability Profile への OAuth 詳細取り込み) のレビューサイクル進行**: 前年 12/21 に appsdesh (Apoorva Deshpande) が起票した PR が、1/9 コール議題として **「言葉遣いを『OAuth のプロファイル』から『SSF Transmitter と組み合わせて使う OAuth サーバーのプロファイル』に変える」** という方向で詰められた。1/9 に Apoorva が「Atul's feedback」commit (`d4222f`)、1/11 に追加 commit (`5e5938`, `25672d`)、1/16 に「Shayne's suggestion / CAEP version」commit (`c4f0f8`) を投入。tulshi が 1/11 に承認したが、本月内に `main` へは merge されず（最終 merge は 6/10）
- **3/4-5 Gartner IAM Summit London Interop Event の準備加速**: 2023-12-21 公開・2024-01-06 改訂の [Call for Participation](https://openid.net/call-for-participation-demonstrate-interoperability-of-your-caep-implementations/) アナウンスのもと、1 月は (i) 1/12 関心表明締切 (1/6 から延長)、(ii) 1/17 OIDF による use case 確定、(iii) 1/27 interop profile 最終化レビュー、というマイルストンを消化する月となった。1/9 コールでは「Gartner が implementor の demo 用 venue をホストする」「週次 30 分の interop ミーティングを別途設定して use case 案出と spec 更新を行う」ことが合意された

`openid-specs-risc` ML の本月の人手投稿は **9 件**（1/3 Mike Leszcz Board Elections、1/9 Atul Call notes、1/11 Tom Sato Hybrid Workshop、1/16 andrei-galkin Issue #138 起票、1/16-19 週内に Apoorva (推定) Issue #138 への返信、1/23 Atul + Gail Hodges + ALI Asad の新議長就任スレッド、1/29 Tom Sato OAuth Security Workshop CFS と Authenticate 2024 CFS、1/31 Gail Hodges OECD ITAC 転送）。これに加えて GitHub bot 通知 (Issue #136 Test/closed、Issue #137 commits / Issue #138 起票・コメント / Issue #139 起票 / PR #134 commits) が断続的に流れた。

定例 WG コールは隔週運用下で **1/9 と 1/23 の 2 回開催**。

## 3. ミーティングと議論

1 月の WG 定例コールは隔週運用下で 2 回開催 (**1/9、1/23**)。議事録は [github.com/openid/sharedsignals/wiki/Meetings](https://github.com/openid/sharedsignals/wiki/Meetings) からリンクされた HackMD ページに公開されている。

### 3.1 2024-01-09 定例 WG コール

参加者: Atul Tulshibagwale (SGNL)、Apoorva Deshpande (Okta)、Tom Sato (VeriClouds)、Shayne Miel (Cisco)、Peter Travers (MongoDB)、Mike Kiser (SailPoint)、Stan Bounev (VeriClouds)、Sean O'Dell (Disney)（議事録 [HackMD 2024-01-09](https://hackmd.io/@oidf-wg-sse/wg-meeting-20240109) より）。Atul が議事録要旨を当日中に ML に共有 (msg 001432)。アジェンダは「Interoperability Spec PR」「Opaque Format PR」「共同議長交代」「Interop ミーティングと Gartner Event」「Use Case」「Tokyo OpenID Event」の 6 本立て。

主要議論:

- **Interoperability Spec PR (#134) の OAuth 位置づけ整理**: Apoorva の起票内容について議論。仕様の言い回しを **「OAuth のプロファイル (a profile of OAuth)」** ではなく **「SSF Transmitter と組み合わせて使うときの OAuth サーバーのプロファイル (a profile of an OAuth server when used with an SSF Transmitter)」** とする方向で合意（議事録 2024-01-09 より）。これは「SSF が OAuth そのものを改変するわけではない」というスコープの明確化であり、後の 2/6 コールでの OAuth セキュリティ十分性論争 (Shayne の Duo 用途反論、Aaron の 2 層プロファイル案) の前段となる

- **Opaque Format PR (#137) の適用範囲**: Verification event と subject identifier の関係について議論。**「opaque 形式は verification events 専用に限定すべきか」** という論点が提起され（議事録 2024-01-09 より）、Shayne がアクションアイテムとして **「opaque format を verification events 専用に restrict する」** を引き取った。これを受けて 1/11 に追加 commit (`ffdf2c`: "Add disclosure about opaque being for the Verification...") が投入され、1/15 に PR は merge された

- **共同議長交代 (Anabelle 退任、Shayne / Sean 就任予定)**: Atul が **「Anabelle が共同議長を辞任する。Shayne Miel と Sean O'Dell が後任就任に関心を表明した。次回コール (1/23) までに反対意見がなければ正式承認する」** と告知。WG ガバナンスにおける標準的な lazy-consensus 手順

- **Interop ミーティングと Gartner Event**: 通常の隔週コールとは別に **「週次 30 分の Interop 専用ミーティング」** を新設することを合意。Gartner が implementor の Transmitter / Receiver プロトタイプ demo 用 venue をホストすることが共有された

- **Use Case 開発の重要性強調**: 参加者から **「セキュリティツールが組織の課題をどう解決するかを示す『エンドツーエンドの叙述 (end-to-end narrative)』を開発することが重要」**（議事録 2024-01-09 より）との主張。CIAM 文脈では device identifier を用いた targeted session revocation のような具体的シナリオが議論された

- **Tokyo OpenID Event の告知**: VeriClouds (Tom Sato / Stan Bounev) が、1/18 KDDI Office での OpenID Japan Summit (300+ attendees 予定) で SSF overview をプレゼンする予定を共有

- **アクションアイテム**:
  - Shayne: opaque 形式を verification events に限定する文言を PR #137 に追加
  - Apoorva: CAEP のバージョニング情報を interoperability 仕様に含める
  - Stan / Sean: リポジトリに use case ドキュメンテーションを寄与する

### 4.4 [openid/sharedsignals: New Issue opened (#138 — Hypothetical SET of Login)](https://lists.openid.net/pipermail/openid-specs-risc/Week-of-Mon-20240115/001438.html) - andrei-galkin via GitHub bot, 2024-01-16

> 「Hi - which RFC are you referring to? SSF and SSF events are defined in OpenID specifications which are profiles of various IETF RFCs. If you're looking for a way to signal a logout event, the CAEP Session Revoked event may work for the use case: https://openid.net/specs/openid-caep-specification-1_0.html#rfc.section.3.1」

外部 issue として open のまま継続。WG として「特定 RFC への login event 例追加」というスコープではなく「CAEP Session Revoked 等の既存イベントの活用案内」という方向で response がなされた。

### 4.5 [Fwd: [OECD ITAC] security researchers "safe harbours" 専門家インタビュー要請](https://lists.openid.net/pipermail/openid-specs-risc/Week-of-Mon-20240129/001447.html) - Gail Hodges (OIDF Executive Director), 2024-01-31

Gail Hodges が OECD Digital Security 部門 (Bénédicte Schmitt) からの転送として、2022 年 OECD Council Recommendation on Vulnerability Treatment に基づく safe harbour 政策ガイダンス策定のための **「脆弱性研究者保護に関する専門家インタビュー」** への参加を呼びかけ。

インタビュー観点には (i) 現状の法的保護と改善点、(ii) safe harbour 実装の障壁、(iii) 研究者保護の理想的なスコープ、(iv) 立法を超えた政策アプローチ、(v) 不当な訴訟脅威への対策、(vi) 研究者倫理、(vii) chartered profession 化の検討、が含まれる。Gail は **「Shared Signals は『改善されたセキュリティインフラがより広いエコシステムにどう便益をもたらすか』を示す具体例となりうる」** と参加意義を強調。直接的な技術議論ではないが、SSF / CAEP の対外政策コンテキストとして WG メンバーへの認知共有が図られた。

- 月内承認: tulshi (2024-01-11), appsdesh (2024-01-11)

PR 本文の主張:

> 「Verification events MUST include an opaque sub_id. Since Transmitters MUST send verification events, then Receivers MUST be prepared to accept them.」

すなわち SSF Receiver が必ず受領しなければならない verification event においては subject identifier として `opaque` 形式を必須化すべき、というロジック。これは Receiver 実装の最小要件を明確化する変更で、interop の implementer 間 ambiguity 解消を狙ったもの。

1/9 コールでの議論を受け、当初の「全 subject format に opaque を必須化」という案から **「opaque 形式は verification events に限定する」** へとスコープが絞られ、1/11 に FragLegs が追加 commit `ffdf2c` ("Add disclosure about opaque being for the Verificat...") を投入。これにより一般の event では従来通り `email` / `phone` / `iss-sub` / `aliases` 等の subject identifier formats が継続利用できる構造が維持された。

承認は tulshi (Atul) と appsdesh (Apoorva) が 1/11 中に揃い、timcappalli のレビューを待たずに 1/15 に merge された (`7b00ef9`)。merge 直前の最終形には Apoorva が PR #134 (oauth-interop ブランチ) で行っていた作業との競合はなく、独立した変更として完結している。

### 5.2 [openid/sharedsignals#134](https://github.com/openid/sharedsignals/pull/134) — Include OAuth specifics in the interop spec

- author: appsdesh (Apoorva Deshpande, Okta)
- 起票: 2023-12-21（前年起票だが 1 月内に多数の活動があり継続審議の主要 PR）
- 1 月内コミット数: 4 件 (`d4222f`, `5e5938`, `25672d`, `c4f0f8`)
- 1 月内承認: tulshi (2024-01-11) / 状態: open（最終 merge は 2024-06-10）

PR の意図は **「OAuth 2.0 を interoperability draft の authorization scheme として確立し、vendor interop を標準化するために OAuth 構造の使用に関する詳細を追加する」**。1/9 コールで議論された結果、文書の表現を **「OAuth のプロファイル」から「SSF Transmitter と組み合わせて使うときの OAuth サーバーのプロファイル」へ** 修正する方向で詰められた。

1 月内の commit 履歴:

- 1/9: `d4222fda` "Atul's feedback" (oauth-interop ブランチ、Apoorva push) — 1/9 コール中の tulshi フィードバックを反映
- 1/11: `5e59386f` "Include OAuth specifics in the interop spec" + `25672dae` 同名 + `fd3bcd` merge commit — 追加のリビジョン
- 1/16: `c4f0f85e` "Shayne's suggestion / CAEP version" (Apoorva push) — Shayne の提案と CAEP バージョニング情報の取り込み

tulshi (Atul) は 1/11 に approve したが、Apoorva は 1/16 に FragLegs と tulshi に対し追加レビューを再要求しており、本月内には完結しなかった。レビューサイクルは 3 月以降も継続し、最終 merge は 6/10。

### 5.3 [openid/sharedsignals#138](https://github.com/openid/sharedsignals/issues/138) — The Hypothetical Security Event Token of Login

- author: andrei-galkin (外部参加者)
- 起票: 2024-01-16 / 状態: open
- ラベル: `enhancement`, `spec:CAEP`
- 月内コメント数: 1 件 (WG メンバーからの応答、ML msg 001440 として転送)

Issue 本文の趣旨:

> 「I have checked the RFC and was not able to find any example of login.」

login security event token の具体例を RFC ドキュメントに含めることを要望。標準 JWT claim (`iss`, `sub`, `aud`, `iat`, `jti`, `sid`) と `backchannel-logout` を含む event objects の hypothetical JSON 構造を提案。

これに対する WG 側コメント:

> 「Hi - which RFC are you referring to? SSF and SSF events are defined in OpenID specifications which are profiles of various IETF RFCs. If you're looking for a way to signal a logout event, the CAEP Session Revoked event may work for the use case」

CAEP Session Revoked event (CAEP 1.0 §3.1) の参照を案内し、SSF / SSF events が「OpenID 仕様であって IETF RFC ではない」点を整理。Issue は open のまま継続（後の月で正式な対応に至らず close される運び）。WG が外部参加者からの問い合わせに対して既存 CAEP 仕様への誘導で対応した代表例。

なお Issue #139 (1/30 起票、FragLegs author、"CAEP spec has subject in the examples") は本月内コメント 0 件だが、`bug` / `vID-03` ラベルが付与され、6/15 の Implementer's Draft 3 リリース目標を視野に入れた cleanup タスクとして位置付けられた。**「event schemas に未定義の `subject` claim が normative examples に残存している」** という整合性問題で、SET レベルの `sub_id` を正式機構として examples を整理する方針。
